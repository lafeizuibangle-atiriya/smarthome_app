# 智慧家居项目技术选型报告

> 项目名称：仿米家智慧家居 App（含真实硬件接入）
> 文档版本：v2.0（2026-11-20）
> 关联文档：《11_智慧家居项目需求报告》

---

## 一、总体架构与选型概览

系统分为四层，各层选型如下：

| 层 | 选型 | 版本 | 说明 |
|---|---|---|---|
| 移动端 | HarmonyOS ArkTS / ArkUI | API 12 | 鸿蒙原生应用，DevEco Studio 开发 |
| 服务端 | Spring Boot + MyBatis-Plus + Hutool | 3.3.4 / 3.5.7 / 5.8.27 | JDK 17，Maven 构建 |
| 数据库 | MySQL + Redis | 8.0 | Redis 用于验证码与缓存 |
| 物联网云 | 华为云 IoTDA（设备接入服务） | 标准版 | 设备 MQTT 接入、AMQP 数据转发、命令下发 |
| 设备端 | STM32 + ESP8266（Keil MDK，C 语言） | — | 传感器采集与执行器驱动，MQTT 接入云平台 |

整体数据流：设备传感器 → MQTT 上报华为云 → 数据转发规则推送 AMQP → 后端订阅同步入库 → App 轮询读取；反向：App 发起控制 → 后端调华为云命令接口 → 华为云下发 MQTT 命令 → 设备执行。

## 二、移动端选型

### 2.1 框架：HarmonyOS ArkTS + ArkUI（声明式）

| 备选 | 结论 | 理由 |
|---|---|---|
| HarmonyOS ArkTS/ArkUI | **选用** | 鸿蒙生态主流方向；声明式 UI 开发效率高；课程要求与个人发展方向一致 |
| uni-app / Flutter 跨端 | 不选 | 无法体现鸿蒙原生能力；ArkTS 严格模式对代码规范要求更高，教学价值大 |
| Web App | 不选 | 无法申请设备相关权限，演示效果差 |

关键约定：所有网络请求收口到 `api/` 目录（页面禁止直接拼 URL）；数据模型统一放 `model/`；`HttpClient` 统一带 token、统一 401 处理与提示节流；列表渲染 ForEach 的 key 包含会变的数据字段，保证轮询数据能刷新。

### 2.2 状态与刷新策略

采用 1 秒 HTTP 轮询获取首页总览（一次请求带回房间、设备、环境、模式），配合 AMQP 秒级推送，全链路最坏延迟约 2 秒。未登录不发请求、切走 Tab 停止轮询，避免无效请求与提示刷屏。

## 三、服务端选型

### 3.1 框架：Spring Boot 3.3.4

| 备选 | 结论 | 理由 |
|---|---|---|
| Spring Boot 3.3.4 | **选用** | 生态成熟、三层架构清晰，JDK 17 虚拟线程与语法改进可用；团队成员均有 Java 基础 |
| Node.js (Express) | 不选 | 类型约束弱，不适合多人分模块协作 |
| Spring Cloud 微服务 | 不选 | 单体足够，微服务增加部署与调试成本 |

### 3.2 ORM：MyBatis-Plus 3.5.7

单表 CRUD 使用 BaseMapper 零 SQL，复杂查询用 LambdaQueryWrapper；相比 JPA 更贴合国内主流与教学场景，相比裸 MyBatis 减少大量样板代码。

### 3.3 工具库：Hutool 5.8.27

JWT 签发校验、JSON 解析、HTTP 调用（天气代理、华为云 API）统一使用 Hutool，不额外引入 SDK。经验教训已内化为规范：JWT 校验必须用 `validate(0)`（同时验签名与有效期）；解析 JSON 前过滤 null 值，避免 null 进入下游序列化。

### 3.4 鉴权与安全

| 项 | 选型 | 说明 |
|---|---|---|
| 认证 | JWT（Hutool）+ 拦截器 | 默认全拦截 + 白名单放行登录注册 |
| 密码存储 | BCrypt 加盐哈希 | 库中无明文 |
| 指令安全 | 后端 `sanitizeAction()` 清洗 | 只读字段丢弃、越界拒绝、枚举白名单，安全边界划在后端 |
| 邮件 | QQ SMTP + Redis 验证码 | 60 秒冷却、验证码一次性 |

### 3.5 与华为云的对接方式

| 项 | 选型 | 理由 |
|---|---|---|
| 属性上报接收 | AMQP 订阅（qpid-jms-client 0.61.0） | 华为云数据转发规则推送消息到 AMQP 队列，秒级到达，优于 HTTP 轮询查询设备影子 |
| 命令下发 | 华为云 IoTDA REST API（Hutool HttpUtil） | 复用现有 HTTP 工具，不引入额外 SDK |
| 数据同步 | HuaweiSyncService 统一处理 | 属性上报解析后回写 device 表与 room_environment 表，数据库状态始终以硬件为准 |

## 四、数据库选型

MySQL 8.0，16 张表，InnoDB。关键设计决策：

| 决策 | 说明 |
|---|---|
| 设备状态用 JSON 字符串字段 | 不同类型设备字段差异大，JSON 避免为每种类型建表；配合后端 DeviceTypes 字典类约束字段 |
| 金额用 DECIMAL(10,2) | 禁用 float，避免精度问题 |
| 订单明细快照 | 冗余商品名与图片，商品下架改价不影响历史订单 |
| 全表带 user_id | 接口按登录人过滤，实现数据隔离 |
| SQL 单一自包含脚本 | init_all.sql 建库建表加演示数据一体，可反复执行，导入时强制 utf8mb4 |

Redis 用于邮箱验证码存储（冷却与一次性校验）与天气缓存。

## 五、物联网云平台选型

### 5.1 平台：华为云 IoTDA 标准版

| 备选 | 结论 | 理由 |
|---|---|---|
| 华为云 IoTDA | **选用** | 与鸿蒙生态同源（课程与就业方向匹配）；免费额度满足课程项目；AMQP 推送、命令下发、设备影子、消息跟踪等调试工具齐全 |
| 自建 EMQX + Mosquitto | 不选 | 需自行维护broker 高可用与规则引擎，工程量超出课程范围 |
| 涂鸦 / 阿里 IoT | 不选 | 平台闭源程度高，调试与教学资料不如华为云开放 |

### 5.2 接入与转发设计

| 项 | 选型 | 说明 |
|---|---|---|
| 设备接入协议 | MQTT（TLS，1883/8883） | ESP8266 直连华为云 MQTT 接入点 |
| 数据转发 | 数据转发规则 → AMQP 推送消息队列（DefaultQueue） | 必须创建并启动规则才会推送；后端以 AMQP 客户端订阅消费 |
| 命令下发 | 同步命令 REST API | 命令名与固件侧约定：Light_control、Motor_control、Servo_control、Beep_control、Mode_control |
| 模型定义 | service_id=smart_home，属性含 Temperature/Humidity/Lux/LightStatus/MotorStatus/ServoStatus/BeepStatus/ModeStatus/SmokeStatus/PIR_Status | 设备端与后端字段名严格对齐 |

## 六、设备端选型

### 6.1 硬件与固件

| 项 | 选型 | 说明 |
|---|---|---|
| 主控 | STM32（Keil MDK 5，C 语言） | 实训平台现成板卡，实时性满足联动控制 |
| 联网模块 | ESP8266（AT 指令，透传 MQTT） | 成本低、资料多 |
| 传感器 | 温湿度、光敏（Lux）、人体感应 PIR、烟雾 | 覆盖环境监测与安全报警场景 |
| 执行器 | LED 灯、直流风扇（电机）、舵机（自动门）、蜂鸣器 | 与 App 控制的设备一一对应 |

### 6.2 设备端软件设计要点

| 项 | 设计 | 理由 |
|---|---|---|
| 联动逻辑位置 | 固件内实现（光控灯、温控风扇带 2℃ 滞回、PIR 控门 5 秒延时） | 云端或后端做联动会增加链路延迟；本地联动断网也能工作 |
| 烟雾报警 | 任何模式生效，蜂鸣器 + 风扇，不动作自动门 | 安全优先级最高，跨模式可靠触发 |
| 上报策略 | 周期 500ms，且计时点在本次上报完成后 | 上报是阻塞操作（等待 AT 应答），完成后计时保证不会出现指令堆积 |
| 模式切换 | 云端命令（Mode_control）与板上按键（KEY4）双通道 | 云端命令供 App 使用，本地按键供现场调试 |
| 消抖 | 烟雾等开关量信号连续多次确认才触发 | 避免传感器抖动导致误报 |

### 6.3 早前方案对比（为什么最终走华为云）

项目早期规划过"设备 HTTP 直连后端"方案（设备模拟器 + 板子直接 POST 后端接口）。该方案链路短，但存在三个问题：设备需要长期有效 token 的鉴权方案、无法使用云平台的设备管理与调试工具、不符合真实智能家居"设备接入云平台"的产品形态。最终改为设备接入华为云、后端与云平台交互的标准形态，设备与 App 职责彻底分离。

## 八、风险与应对

| 风险 | 应对 |
|---|---|
| 设备端上报频率过高导致 AT 指令堆积、设备无响应 | 上报完成后再计周期；实测异常时降低频率或改为"数据变化才上报 + 固定心跳" |
| 华为云免费额度 / 转发规则配置失效 | 消息跟踪页面定位问题；规则未启动、resource 字段变化均有排查路径 |
| AMQP 消息重复推送 | 后端按"值未变化不写库"幂等处理；检查转发规则避免重复建规则 |
| 校园网络不稳定 | 设备端断线自动重连 MQTT；App 请求失败统一提示与节流 |

## 九、选型结论汇总

| 决策项 | 结论 |
|---|---|
| 移动端 | HarmonyOS ArkTS/ArkUI 原生开发，1 秒轮询 + 统一网络层 |
| 服务端 | Spring Boot 3.3.4 单体三层 + MyBatis-Plus + Hutool |
| 数据库 | MySQL 8（JSON 状态字段、单一自包含 SQL）+ Redis（验证码/缓存） |
| 物联网平台 | 华为云 IoTDA：MQTT 接入、AMQP 数据转发、REST 命令下发 |
| 设备端 | STM32 + ESP8266，联动逻辑在固件内，上报完成计时防堆积 |
| 安全 | JWT + BCrypt + 后端指令白名单清洗 |
| 天气 | 和风天气，后端代理 + 缓存 |
| 支付 | 模拟支付（课程边界，不接真实渠道） |
