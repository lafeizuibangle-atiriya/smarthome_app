## 1. 项目背景与目标

### 1.1 背景

智能家居设备普遍存在"各家 App 管各家设备"的割裂问题。本项目以米家 App 为交互参照，在一套实训箱硬件（STM32 + ESP8266 上云）之上，实现一个覆盖"设备控制、自动化场景、环境监测、商城下单"全链路的智慧家居 App。

### 1.2 目标

1. 用户通过 App 远程查看和控制家中设备（灯、风扇、自动门、蜂鸣器、各类传感器），端到端延迟不超过 1 秒；
2. 支持全屋自动/手动模式切换，自动模式下按环境数据联动设备（天黑开灯、烟雾报警响蜂鸣器开风扇等），联动逻辑符合现实常识；
3. 内置商城模块（商品浏览、购物车、下单、支付、订单管理），下单接口具备幂等能力，重复提交不产生重复订单；
4. 后端接口具备参数校验、全局异常处理、分页查询、JWT 鉴权等基础工程质量保障，压测吞吐满足课程演示规模。

## 2. 系统总体设计

### 2.1 技术栈

| 层 | 技术 | 版本 |
|---|---|---|
| 客户端 | HarmonyOS ArkTS / ArkUI | API 12+ |
| 服务端 | Spring Boot + MyBatis-Plus + Hutool | 3.3.4 / 3.5.7 / 5.8.27 |
| 数据库 | MySQL | 8.0 |
| 缓存 | Redis（验证码、订单幂等键） | 7.x |
| 硬件 | STM32（Keil）+ ESP8266，接入华为云 IoTDA | — |
| 云平台 | 华为云 IoTDA（设备接入 + AMQP 订阅上报） | 标准版 |
| 部署 | Docker Compose（App + MySQL + Redis + Prometheus + Grafana） | — |

### 2.2 数据链路

```
实训箱传感器 ──500ms 周期上报──> 华为云 IoTDA ──AMQP 订阅──> Spring Boot 后端 ──> MySQL
                                                                     │
HarmonyOS App <──────HTTP/JSON（1 秒轮询）────────────────────────────┘
```

### 2.3 模块划分

| 模块 | 内容 | 对应接口前缀 |
|---|---|---|
| 用户 | 注册（账号/邮箱验证码）、登录（JWT）、个人信息 | /api/user |
| 首页 | 全屋总览、全屋模式切换、房间管理 | /api/home、/api/room |
| 设备 | 设备增删改查、控制下发、操作日志（分页） | /api/device |
| 环境 | 房间温湿度/光照/烟雾查询与手动刷新 | /api/room/{id}/environment |
| 场景 | 预设场景（回家/离家/晚安）配置与执行 | /api/scene |
| 商城 | 商品、购物车、订单（含幂等下单） | /api/goods、/api/cart、/api/order |

## 5. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 华为云 IoTDA 凭证失效 / 设备离线 | 控制下发失败 | 后端保留本地状态兜底，下发失败不影响状态记录与展示 |
| 500ms 上报周期在高并发下丢包 | 环境数据跳变 | 预留"变化才上报 + 1s 心跳"降级方案，改 Keil 常量即可 |
| 数据库密码 / 云平台凭证泄露 | 安全风险 | 验收后修改 demo 数据库密码与 IAM 子用户密码（见部署手册 6 节） |
| 组员进度不确定 | 交付延期 | 关键路径由组长兜底，模块间用接口文档解耦 |
| Redis 未启动导致幂等/验证码失效 | 下单重复、邮箱注册不可用 | compose 编排内置 redis 服务并配健康检查 |

## 6. 验收与交付标准

1. 功能验收：按《16_验收单》逐项通过，含正常/异常/边界三类场景；
2. 性能验收：JMeter 数据——总览接口 495 TPS（50 并发）、登录 37 TPS（BCrypt 设计开销）、0 错误；
3. 自动化验收：Pytest 59 条接口用例全部通过（test_api/report/report.html）；
4. 部署验收：docker compose up -d 一键启动后，App 连接 8080 端口全功能可用；
5. 培训交付：完成用户培训讲解（配套 PPT），演示账号 demo/123456 可复现全部演示效果。
