## 一、五项能力盘点与改动

| 能力 | 改造前 | 改造内容 |
|---|---|---|
| JWT 登录鉴权 | 已有（LoginInterceptor + JwtUtil） | 无需改动，盘点确认实现正确（见 1.1） |
| 全局异常处理 | 已有骨架，兜底 500 泄露异常消息 | 补参数校验异常处理；收紧兜底返回（见 1.2） |
| 分页查询 | 全项目无分页 | 分页插件 + 2 个分页接口（见 1.3） |

| 接口幂等 | 下单接口连点即重复下单 | Redis SETNX 幂等键（见 1.5） |

### 1.1 JWT 登录鉴权（已有，盘点确认）

- 拦截器统一校验请求头 `token`，通过后 `request.setAttribute("userId", ...)` 放行。
- 关键实现点：校验用 `jwt.validate(0)`（签名 + 有效期一起验；`verify()` 只验签名是已知陷阱）；payload 数字先转 `Number` 再 `longValue()`（Hutool 解出的是 NumberWithFormat）；解析失败打 WARN 不静默。
- 拦截器在 Controller 之前执行，异常不走 `@RestControllerAdvice`，所以 401 响应是拦截器里手写的 JSON，字段名与 `Result` 对齐。

### 1.2 全局异常处理（增强）

`GlobalExceptionHandler` 新增两类处理并收紧兜底：

| 异常 | 返回 | 说明 |
|---|---|---|
| `BizException` | 400 + 业务提示 | 原有 |
| `MethodArgumentNotValidException` | 400 + "字段名：原因" | 新增，配合参数校验 |
| `HttpMessageNotReadableException` | 400 "请求体格式错误" | 新增，拦住 Content-Type 传错的调用 |
| `Exception`（兜底） | 500 "服务器繁忙，请稍后重试" | **收紧**：原来返回 `e.getMessage()`，会把内部实现细节暴露给客户端；现在只记日志不回传 |

### 1.3 分页查询（新增）

- 新增 `MybatisPlusConfig` 注册 `PaginationInnerInterceptor`（MySQL 方言）。**没有这个 Bean 时 MyBatis-Plus 的 selectPage 是假分页（全表查出再截取）**，这是最容易忽略的一步。
- 新增通用返回 `PageVO<T>`（list / total / pageNum / pageSize 四个字段，不把框架的 Page 对象直接序列化给前端）。
- 新增两个分页端点（原接口保留，老客户端不受影响）：

| 端点 | 说明 |
|---|---|
| `GET /api/device/{id}/logs/page?pageNum=&pageSize=` | 设备操作日志分页 |
| `GET /api/order/page?status=&pageNum=&pageSize=` | 订单列表分页 |

- 两处实现都做了 pageSize 上限 50（防恶意大页一次拉爆内存）与 pageNum 下限 1。
- 验证：日志分页返回 `{"list":[...],"total":...}` 结构正确；订单分页空列表返回 `total:0`。

### 1.4 参数校验（新增）

- pom 新增 `spring-boot-starter-validation`；Controller 入参统一加 `@Valid`。
- 11 个 DTO 全部加注解：`@NotBlank`（登录/注册/房间/设备名）、`@Size`（用户名≤20、密码 6~32 位、房间名≤10）、`@Email`（邮箱）、`@Pattern`（手机号 `^1[3-9]\d{9}$`、验证码 6 位数字、设备类型、订单 requestId）、`@Min/@Max`（购物车数量 1~99）、`@NotNull/@NotEmpty`（订单地址与商品列表）。
- 分层原则：格式/边界校验放 DTO 注解（声明式、一处生效），业务校验（库存够不够、地址是不是你的）仍在 Service。
- 验证：空用户名登录返回 `{"code":400,"msg":"username：用户名不能为空"}`。

### 1.5 接口幂等（新增，下单接口）

**问题**：下单涉及扣库存 + 插订单两个写操作。网络超时重试、用户连点会生成重复订单、重复扣库存。

**方案**：客户端生成 `requestId`（UUID）作为幂等键，重试时复用同一值；后端用 Redis SETNX 占位：

```
SETNX order:idem:{userId}:{requestId} "processing" EX 60
  ├─ 成功 → 真正下单 → 结果缓存 result 键（10 分钟）→ 返回
  ├─ 失败 → result 键有值 → 返回第一次的订单（幂等）
  └─ 失败 → 无 result 键 → "订单正在处理中，请勿重复提交"
下单异常 → 删除占位键 → 允许同一 requestId 重试
```

占位键 1 分钟过期，防异常中断后永久锁死；失败释放占位保证可重试；不传 requestId 走旧行为（兼容旧客户端）。

**验证**：同一 requestId 连续提交 3 次，3 次返回同一个 orderNo（20261123113835854），只产生一单。

**待接入**：App 端 `OrderApi.createOrder` 尚未传 requestId（后端兼容不传），计划 App 侧在提交订单页生成 UUID 填入。

## 二、JMeter 压测与调优

### 2.1 环境

| 项 | 值 |
|---|---|
| 被测 | Spring Boot 3.3.4（内嵌 Tomcat），本机 localhost:8080 |
| 数据库 | MySQL 8.0 本机，smart_home 库（7 设备 / 3 房间） |
| 压测机 | 同一台机器（JMeter 5.6.3 命令行模式 `-n -t -l`） |
| 脚本 | overview：50 线程 ramp 10s × 100 轮 = 5000 请求；login：20 线程 ramp 5s × 10 轮 = 200 请求 |

### 2.2 基线数据（调优前）

| 接口 | 请求量 | TPS | 平均延迟 | P100 | 错误率 |
|---|---|---|---|---|---|
| GET /api/home/overview | 5000 | **491.2/s** | 3ms | 31ms | 0 |
| POST /api/user/login | 200 | **37.1/s** | 62ms | 88ms | 0 |

基线期间的异常发现：**10 秒压测向后端控制台刷了 30MB SQL 日志**——
MyBatis `StdOutImpl` 把每条 SQL 同步打印，overview 一次要打 10+ 条语句的 Preparing/Parameters/Row 全文。

### 2.3 调优动作

| 改动 | 内容 | 原因 |
|---|---|---|
| ① 关闭 SQL 控制台打印 | `log-impl` 改 `NoLoggingImpl`（调试时改回 StdOutImpl） | 同步控制台 IO，高并发下是磁盘与 CPU 的无谓消耗 |
| ② 调 HikariCP 连接池 | `maximum-pool-size` 10（默认）→ 20 | 50 并发线程竞争 10 个连接会排队取连接 |

### 2.4 调优后数据

| 接口 | 基线 TPS | 调优 TPS | 基线平均延迟 | 调优平均延迟 | 错误率 |
|---|---|---|---|---|---|
| GET /api/home/overview | 491.2/s | **495.0/s** | 3ms | **2ms** | 0 |
| POST /api/user/login | 37.1/s | 37.2/s | 62ms | 61ms | 0 |

调优后日志量：同样压测强度下 30MB → **4.7KB**（SQL 不再打印，只剩框架日志）。

### 2.5 结果分析（为什么 TPS 提升不明显）

诚实结论：overview TPS 只从 491 到 495（+0.8%），平均延迟 3ms→2ms。原因：

1. **被测环境太小**：localhost 回环 + 7 台设备的小库，单次查询本身 <1ms，日志 IO 还没成为主要瓶颈就先到达了"请求处理太快、并发上不去"的区间。
2. **真正拖慢 30MB 日志的收益体现在磁盘与内存**：持续高压或日志输出到 IDE 控制台（同步刷新 UI）时该开销会被放大；压测窗口只有 10 秒，吞吐差异体现不出来。
3. **login 接口 TPS 与延迟几乎不变是设计使然**：62ms 是 BCrypt 加盐哈希的刻意 CPU 开销（安全属性，不是性能缺陷）。它的正确调优方向不是提速，而是防刷（限流/验证码），本次不做。

**验收标准角度的结论**：本项目 App 是 1 秒 1 请求的轮询模型，单用户 QPS≈1；当前 495 TPS 意味着后端可支撑约 500 个用户同时在线，对课程项目有 500 倍余量，性能不构成瓶颈。压测的价值在于验证了 0 错误率、确认了日志与连接池两个配置隐患，并把"瓶颈在 BCrypt 设计开销"这个判断变成了有数据的结论。

### 2.6 压测产物

| 文件 | 说明 |
|---|---|
| `tools/jmeter_overview.jmx` / `tools/jmeter_login.jmx` | JMeter 测试计划（可复跑） |
| `tools/overview_baseline.jtl` 等 4 个 .jtl | 基线/调优两轮原始结果（可导入 JMeter 生成 HTML 报告） |
