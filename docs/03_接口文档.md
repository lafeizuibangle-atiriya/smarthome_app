# 接口文档（前后端契约）

> **这份文档是前后端唯一契约。** 顺序永远是：**先改本文档 → 再改后端 Controller/Service → 再改前端 `ets/api/` → 同步到群里。**
> 前端所有 URL 只能出现在 `ets/api/` 目录（页面里不准写裸 URL）；本文档与后端 Controller 一一对应。
> 本文档同时是**命名规范手册**：新增接口的路径、方法名、字段名，全部按第一章的规则取名，不许自创。

**技术口径**：后端 Spring Boot 3.3.4 + MyBatis-Plus；前端 HarmonyOS ArkTS；统一响应壳 `Result<T>` = `{code, msg, data}`。

## 一、统一规范

**新增任何接口前，先读这一章。** 下面 7 条是全员统一口径，改一处必须全链路一致。

### 1.1 路径规范

| 规则 | 说明 | 样例 |
|------|------|------|
| 前缀 | 全部以 `/api` 开头 | `/api/device/list` |
| 资源名 | **单数**（骨架期定的，全项目沿用，不要改成复数） | `/api/device`、`/api/room`、`/api/order` |
| 层级 | 不超过 3 段；父子关系写成"父/子资源" | `/api/room/{roomId}/environment` |
| 动作 | 状态机动作放**最后一段动词** | `/api/order/{id}/pay`、`/api/scene/{id}/run` |
| 路径变量 | 唯一主体用 `{id}`；父子关系里用父资源名 `{roomId}` | `/api/device/{id}`、`/api/room/{roomId}` |
| 查询参数 | 小驼峰，与 JSON 字段同名；筛"全部"用 `-1` 或空 | `?roomId=1&categoryId=2&keyword=xx&status=-1&position=home&limit=100` |

### 1.2 命名规范（四层一致性）

| 层 | 规则 | 样例 |
|----|------|------|
| 后端 Java 类 | `XxxController` / `XxxService`(+`impl/XxxServiceImpl`) / `XxxMapper` / `XxxVO`（出参）/ `XxxDTO`（入参） | `DeviceController`、`DeviceVO`、`DeviceAddDTO` |
| 后端 Java 方法 | **必须与前端 api 方法同名**（下方动词表里挑） | `DeviceController.control` ↔ `DeviceApi.control` |
| JSON 字段（出入参） | **一律小驼峰**，与 Java 字段名完全一致（不写 `@JsonProperty`、不手动改名） | `roomId`、`categoryId`、`isDefault` |
| 数据库列 | **一律下划线小写**，由 MyBatis-Plus 驼峰映射自动转换 | `room_id` ↔ `roomId`、`create_time` ↔ `createTime` |
| 前端 ArkTS | 文件名 `XxxApi.ets`；方法为 `static`；变量名与 JSON 字段同名 | `DeviceApi.deviceList(roomId)` |

**字段名对照示例**（同一份数据在四层里长什么样）：

| 层 | 房间 | 创建时间 | 是否默认 |
|----|------|---------|---------|
| 数据库列 | `room_id` | `create_time` | `is_default` |
| 后端 Java / JSON | `roomId` | `createTime` | `isDefault` |
| 前端 ArkTS | `roomId: number` | `createTime: string` | `isDefault: number` |

**方法名动词表（新增接口必须从这里挑，不许自创）**

| 动词 | 语义 | 通用签名 | 样例 |
|------|------|---------|------|
| `list` | 查列表 | `list(筛选参数...)` | `GET /api/device/list` |
| `detail` | 查单个（路径带 id） | `detail(id)` | `GET /api/scene/{id}` |
| `add` | 新增 | `add(DTO)` | `POST /api/room` |
| `update` | 修改（body 带 id） | `update(DTO)` | `PUT /api/cart` |
| `rename` | 只改名字（不是全量改） | `rename(id, name)` | `PUT /api/device`、`PUT /api/room` |
| `remove` | 删除 | `remove(id)` | `DELETE /api/device/{id}` |
| `save` | 新增/修改共用同一个 DTO（场景专用） | `save(DTO)` | `POST /api/scene` |
| `control` | 下发设备指令 | `control(id, action)` | `POST /api/device/{id}/control` |
| `run` / `toggle` | 执行一次 / 启停开关 | `run(id)` / `toggle(id, enabled)` | `/api/scene/{id}/run`、`/toggle` |
| `refresh` | 手动触发一次重算/采样 | `refresh(id, 参数可空)` | `/api/room/{roomId}/environment/refresh` |
| `clear` | 清空集合 | `clear()` | `DELETE /api/cart/clear` |
| `create` | 生成一个业务实体（下单） | `create(DTO)` | `POST /api/order/create` |
| `pay` / `cancel` | 状态机流转动作 | `pay(id)` / `cancel(id)` | `/api/order/{id}/pay` |

**前端方法名的两条补充规则**（因为 `list` 在后端重名是正常的，前端要能区分）：

1. 同一个 `XxxApi` 类里有多个 list 时，用「名词 + List」区分：`roomList` / `deviceList` / `addressList` / `goodsList` / `cartList` / `orderList` / `bannerList`（后端保持一致都叫 `list`）；
2. 形参名与 JSON 字段同名；id 类形参统一 `xxxId`（`deviceId`/`roomId`/`sceneId`/`orderId`/`goodsId`），只有"该类里唯一主体"才用 `id`（如 `ProductApi.detail(id)`）。

### 1.3 数据类型与取值规范

| 项 | 统一口径 |
|----|---------|
| **布尔** | **一律 int `0/1`**，禁用 `true/false`。含 `online`、`enabled`、`isDefault`、`hasGas`、`locked`、`watering`、`running`、`cleaning`、`lightOn`、`deodorize`、`nightLight`、`autoFlush`、`smokeAlarm`、`gasAlarm` |
| 布尔命名 | 存量 `isDefault` 保留 `is` 前缀；**新增字段不再加 `is`**，直接用名词（`enabled`/`locked`/`running`） |
| **状态机** | 统一字段名 `status`（数值）：订单 `0 待付款 / 1 已付款 / 2 已完成 / 3 已取消`；查询用 `status=-1` 表示"全部" |
| **分级文案** | 统一 `xxxLevel`，**存中文**（舒适/优/正常/偏高），阈值只在后端维护，前端直接显示，不自己判断 |
| **告警** | 单项统一 `xxxAlarm`（0/1）；聚合计数统一 `alarmCount`（0 = 全部正常） |
| **档位/电平** | `gear`（油烟机 0-3，0 档=关）、`fanSpeed` / `swing`（空调 0-3）、`mode` / `source`（枚举，见设备类型字典） |
| **时间戳** | `createTime` / `updateTime` / `obsTime` 等用 `yyyy-MM-dd HH:mm:ss` 字符串 |
| **定时计划** | 用 `HH:mm` 字符串：`timerOn` / `timerOff` / `waterPlan` / `cronExpr`；**空串 = 取消**（不是 null） |
| **金额** | 后端 `BigDecimal`，JSON 两位小数数字（`price` / `originPrice` / `totalAmount`）；前端不做浮点比较，直接展示 |
| **百分比/强度** | 统一 `0~100` 整数：`brightness`、`openPercent`、`volume`、`filterLife`、`humidity`、`cloud` |
| **温度** | ℃；`temperature` 16~30、`fridgeTemp` 2~8、`freezeTemp` -24~-16、`targetTemp` 35~65、`seatTemp` 30~40（30 = 关） |
| **id** | 后端 `Long`，JSON 数字，前端 `number`；不传字符串形式的数字 |
| **空值** | 统一 `null`（不是 `""`）；**例外**：定时计划字段用空串表示"未设置/取消" |

### 1.4 统一响应结构

```json
{ "code": 200, "msg": "success", "data": null }
```

| 规则 | 说明 |
|------|------|
| 判定 | **前端只看 `body.code`**。业务失败时 HTTP 状态码**仍是 200**，所以判断 HTTP 状态码是错的写法 |
| 唯一例外 | 未登录/token 过期时后端返回 **HTTP 401**（body 里 `code` 也是 401）→ `HttpClient` 中 401 分支优先于"非 200 分支"，会统一清 token、Toast 提示、跳登录页 |
| 列表 data | **直接是数组**（不套 `{list,total}`）；本 Demo 无分页接口，分页统一形态为 `{list,total,page,size}`（备用约定） |
| 写接口 data | `null`（register/add/update/remove/rename/clear/toggle/run），或**操作后的最新对象**（`control`/`water`/`refreshEnvironment`） |
| 最新对象原则 | `control`/`water`/`refreshEnvironment` 返回的 `data` 就是最新状态，**前端直接整体覆盖本地**，不许自己拼状态或只改一半字段 |

### 1.5 鉴权与白名单

| 项 | 约定 |
|----|------|
| 请求头 | `token: <登录返回的 JWT>`；有效期 7 天 |
| 默认口径 | 拦截器 `addPathPatterns("/api/**")` + 白名单（**默认全要登录，显式开白名单**——这样新增接口忘了配也只会"多要登录"，不会"漏鉴权"） |
| 免登录白名单 | `/api/user/login`、`/api/user/register`、`/api/user/email/code`、`/api/user/register/email`、`/api/product/**`、`/api/goods/**`、`/api/banner/**` |
| 需要登录 | 其余全部，**包括天气**（`/api/weather/**`，天气面板在首页，登录后才看得到） |
| 资源归属 | 所有带 id 的读写接口，后端都会校验资源 `user_id` 是否属于当前用户；不属于则返回 `code=400 "xxx不存在"`（不是 403、不是 500） |
| 健康检查 | 用 `GET /api/user/info`：未带 token 返回 `{"code":401,"msg":"请先登录"}` 即表示服务正常 |

### 1.6 错误码

| code | 含义 | 典型 msg |
|------|------|---------|
| 200 | 成功 | `success` |
| 400 | 业务错（参数校验 / 业务规则 / 资源不属于你） | `用户名已存在`、`密码错误`、`库存不足`、`设备不存在`、`没有可执行的控制项`、`温度超出范围`、`验证码错误或已过期` |
| 401 | 未登录 / token 过期 | `请先登录`、`登录已过期` |
| 403 | 无权限 | （暂未使用） |
| 500 | 系统错（兜底异常） | `服务器繁忙`——**出现即视为 bug** |

### 1.7 已知的历史不一致（保留，不再扩散）

| 现状 | 原因 | 结论 |
|------|------|------|
| `/api/goods/banners`（`string[]` 图片名）与 `/api/banner/list`（`Banner[]` 对象）并存 | 前者是首页商城用的轻量版，后者带 `position`/`sort`/`enabled` | 两个都保留；**新页面统一用 `/api/banner/list`** |
| `/api/environment/metrics` 不带 `/device` 前缀，却挂在 `DeviceController` 下 | 环境是"房间属性"，语义上该归 room | 保留现状，见第四章 |
| `/api/oplog/list` 前缀只有 `/api` | `OpLogController` 复用 `/api` 前缀 | 保留 |
| 资源名用单数 `/api/device`、`/api/room` | 骨架期定的，前端已全量引用 | 保留，**不要改成复数** |
| `PUT /api/device`、`PUT /api/room` 用 `rename` 而不是 `update` | 设备/房间只支持改名，语义更准 | 保留（新接口按 1.2 动词表取名） |

### POST /api/user/register

```json
// 请求
{ "username": "zhangsan", "nickname": "小张", "password": "123456" }
// 响应
{ "code": 200, "msg": "success", "data": null }
```

### POST /api/user/email/code

```json
// 请求
{ "email": "3332629064@qq.com" }
// 响应
{ "code": 200, "msg": "success", "data": null }
```

> 验证码 6 位数字，存 Redis，**TTL 60 秒**；同一个邮箱在 60 秒内重复请求会被拒绝（key 还存在 = 冷却中），
> 前端按钮要配合 60 秒倒计时。邮件经 QQ SMTP（`smtp.qq.com:465`）发出。

### POST /api/user/register/email

```json
// 请求
{ "email": "3332629064@qq.com", "code": "123456", "phone": "13800000000",
  "password": "abc12345", "nickname": "大猫" }
// 响应
{ "code": 200, "msg": "success", "data": null }
```

> - `nickname` 可空：为空时后端用**邮箱前缀**兜底；
> - `phone` 必填且唯一（`user` 表有唯一索引）；
> - **username 复用邮箱**——这样普通登录接口 `POST /api/user/login`（username + password）不改也能登录。

### 环境监测模块（房间环境）

环境监测是**房间的属性**，不是某台设备的状态，所以接口挂在 `/api/room/{roomId}/` 下。

#### GET /api/room/{roomId}/environment

| 字段 | 含义 | 正常范围 / 口径 |
|------|------|----------------|
| `temperature` / `temperatureLevel` | 温度 ℃ | 18~28 舒适，<18 偏冷，>28 偏热 |
| `humidity` / `humidityLevel` | 湿度 % | 30~70 舒适，<30 干燥，>70 潮湿 |
| `aqi` / `airLevel` | 空气质量指数 | ≤50 优，≤100 良，≤150 轻度污染，>150 中重度污染 |
| `co2` / `co2Level` | 二氧化碳 ppm | ≤600 清新，≤1500 正常，≤2000 偏高·建议通风，>2000 闷浊·请立即通风 |
| `smoke` / `smokeAlarm` | 烟雾浓度 ppm | ≤20 正常，**>50 触发烟雾报警**（`smokeAlarm=1`） |
| `gas` / `gasAlarm` / `hasGas` | 燃气浓度 ppm | **仅厨房**（`hasGas=1`）返回；≤100 正常，**>200 燃气泄漏**（`gasAlarm=1`） |
| `alarmCount` | 本房间告警项数量 | 0 = 全部正常，前端据此决定是否显示红色告警条 |
| `updateTime` | 最后一次采样时间 | 定时任务每 30 秒更新一次 |

> **厨房判定**：房间名包含 `厨` / `燃气` / `灶` 时，该房间自动开启燃气检测（`hasGas=1`）。
> 普通房间不返回 `gas` 数值（为 `null`**而不是 0**），前端据 `hasGas` 决定要不要渲染"燃气泄漏"那一格。
> 房间还没有环境记录时，后端会**自动初始化一条**，前端不需要先调"创建"接口。

#### POST /api/room/{roomId}/environment/refresh

手动触发一次环境采样。请求体可省略：

```json
// ① 不传 body（或传 {}）= 只采样：各指标在原值附近小幅随机波动
{}

// ② 传字段 = 直接改成该值，用于演示"报警"效果（一键造出告警）
{ "smoke": 120 }                       // 烟雾 120ppm → smokeAlarm=1，面板出现红色告警条
{ "gas": 260 }                         // 燃气 260ppm → gasAlarm=1（仅厨房房间有效）
{ "co2": 1800, "aqi": 180 }            // 触发 CO₂ 偏高 + 空气污染提醒
{ "hasGas": 1 }                        // 现场演示"把这个房间改成支持燃气检测"
```

响应 `data` 是**刷新后的完整环境对象**，前端直接覆盖本地即可，不用等下一轮轮询。

> 未在 body 里指定的指标仍会做一次小幅波动（相当于"手动触发一次采样"）；
> 数值会被夹到物理合理区间（例如温度 -10~50℃），演示时乱填也不会出脏数据。
> 可注入字段（`RoomEnvDTO`）：`temperature`、`humidity`、`aqi`、`co2`、`smoke`、`gas`、`hasGas`。

#### 定时开 / 关在各设备上的语义

定时本身只有"开 / 关"两个动作，落到各类型上由后端翻译：

| type | 定时"开"（`timerOn` 到点） | 定时"关"（`timerOff` 到点） |
|------|--------------------------|---------------------------|
| light / ac / socket / purifier / heater / tv / projector / smoke_sensor / fridge / toilet | `power = on` | `power = off` |
| curtain | `openPercent = 100`（全开） | `openPercent = 0`（全关） |
| pump | `watering = 1`（按 `duration` 浇一次） | `watering = 0`（停浇，并结清水量） |
| lock | `locked = 0`（开锁） | `locked = 1`（上锁） |
| hood | `gear = 1`（low） | `gear = 0`（0 档 = 关） |
| washer / dryer | `running = 1`（开始运行） | `running = 0`（停机） |
| robot | `cleaning = 1`（开始清扫） | `cleaning = 0`（回充） |

> 定时是**每天重复**的：到点执行后不会自动清空，第二天同一时刻还会触发。
> 想取消就把对应字段设成空串。两个定时撞在同一分钟时**关机优先**（不会让灯一直亮着）。

#### 字段校验与只读字段

后端 `DeviceServiceImpl.sanitizeAction()` 会清洗每一条控制指令：

- **只读字段一律丢弃**（由后端或设备上报维护，前端下发不会生效）：
  `powerW`、`energyKwh`（插座计量）、`waterLevel`、`waterStartLevel`、`waterStartTime`、
  `waterEndTime`（水泵水量）、`remaining`（家电剩余时长）、`battery`、`lastUser`、`lastTime`（设备上报）。
- **数值越界直接报错**（`code=400`）：`temperature` 16~30、`brightness` 1~100、
  `openPercent` 0~100、`fanSpeed` 0~3、`swing` 0~3、`volume` 0~100、`gear` 0~3、
  `locked`/`keepOpen` 0/1、`duration` 1~60、`fridgeTemp` 2~8、`freezeTemp` -24~-16、
  `targetTemp` 35~65、`seatTemp` 30~40、`smokeLimit` 10~150、`filterWarn` 5~50。
- **枚举走白名单**：`mode`（空调 cool/heat/dry/fan/auto，洗衣机 standard/quick/bulk/gentle，
  烘干机 low/high/sterilize，扫地机 quiet/standard/strong，投影 cinema/standard/eco）、
  `colorTemp` 只认 2700/4000/6500、`source` 只认 hdmi1/hdmi2/av/tv/cast。
- **时刻格式**：`timerOn`/`timerOff`/`waterPlan` 必须匹配 `HH:mm`（如 `07:30`），空串=取消。
- 清洗后**没有任何可执行项**时返回 `code=400 没有可执行的控制项`
  （典型场景：只发了 `powerW` 这类只读字段）。

> **窗帘口径（重要）**：`openPercent` 就是窗帘的开关——后端收到 `openPercent`
> 会自动联动写 `power`（0 → off，>0 → on），保证卡片开关状态和滑杆永不矛盾。
> 前端窗帘卡片**隐藏**通用电源按钮，开关一律走滑杆。
>
> **水泵口径（重要）**：`watering` 就是水泵的开关——后端收到 `watering`
> 会自动联动写 `power`（1 → on，0 → off），并补上 `duration`、
> `waterEndTime`（预计停止时间，前端拿它显示倒计时）。
> 手动浇水也可以走专用接口 `POST /api/device/{id}/water`。
>
> **水量口径（重要）**：`waterLevel` **只能读、不能写**。开泵时后端记下
> `waterStartLevel`（开浇水位）和 `waterStartTime`（开浇时刻），之后
> 剩余水量 = 开浇水位 − 已浇分钟数（**1%/分钟**，封底 0），由定时任务
> 每分钟推进一次；中途手动停泵也会先把已浇掉的分钟数结清。
> 这个算法是**幂等**的（由起点推算，不是"每跑一次扣一格"），
> 所以定时任务重复执行也不会多扣水。
>
> **门禁口径（重要）**：`locked` 与 `power` **反向联动**——上锁（1）时 `power=off`、
> 开锁（0）时 `power=on`。前端门禁卡片开关的含义是"开锁/上锁"。
>
> **家电运行口径**：`running` / `cleaning` 是洗衣机 / 烘干机 / 扫地机的开关，
> 后端联动 `power` 并补上 `remaining`（剩余分钟，只读）；扫地机按 1%/分钟耗电，
> 电量 ≤10% 时自动停机回充。

### 设备类型字典

| type | 含义 | status 属性（★ = 可下发控制，其余只读） |
|------|------|----------------------------------------|
| light | 灯 | ★power, ★brightness(1-100), ★colorTemp(2700/4000/6500) |

| lock | 智能门禁 | ★locked(0/1), ★keepOpen(0/1)；battery、lastUser、lastTime（**只读**） |
| hood | 油烟机 | ★gear(0-3，0 档=关，power 由后端联动), ★lightOn(0/1) |
| smoke_sensor | 烟雾传感器 | ★power, ★smokeLimit(10-150 报警阈值)；smoke 浓度、battery（**只读**，浓度同步房间环境） |
| fridge | 冰箱 | ★power, ★fridgeTemp(2-8 冷藏), ★freezeTemp(-24~-16 冷冻) |

| purifier | 净水器 | ★power, ★filterWarn(5-50 滤芯告警线)；filterLife（**只读**） |
| heater | 热水器 | ★power, ★targetTemp(35-65) |
| dryer | 烘干机 | ★running(0/1), ★mode(low/high/sterilize)；remaining（**只读**） |
| robot | 扫地机器人 | ★cleaning(0/1，联动 power), ★mode(quiet/standard/strong)；battery（**只读**） |
| toilet | 智能马桶 | ★power, ★seatTemp(30-40，30=关), ★deodorize(0/1), ★nightLight(0/1), ★autoFlush(0/1) |
| tv | 电视 | ★power, ★volume(0-100), ★source(hdmi1/hdmi2/av/tv/cast) |
| projector | 投影器 | ★power, ★volume(0-100), ★mode(cinema/standard/eco) |

> **类型演进**：`temp_sensor`（温湿度计）已移除——环境数据不再是"某台设备的状态"，
> 而是**房间的属性**（见上方「环境监测模块」）。设备类型由 6 种扩到 **17 种**（上表 hood ~ projector），
> 家电运行进度（`remaining`、`battery`）由后端定时任务每分钟推进。

### 定时任务（后端自动，前端无需轮询）

由后端三个定时任务驱动（均在每分钟第 0 秒跑，cron `0 * * * * ?`）：

| 任务 | 职责 |
|------|------|
| 环境采样（30 秒） | 逐房间刷新温度/湿度/AQI/CO₂/烟雾/燃气，落 `room_environment` |
| 浇水任务 | ① `waterPlan` 到点自动开泵；② 推进在浇水水泵的水位（1%/分钟），到 `waterEndTime` 自动停泵 |
| 设备任务 | ① 扫描**所有设备**的 `timerOn`/`timerOff`，按类型翻译成语义字段执行（并写设备日志，文案「定时开机/定时关机」，与手动「控制：…」区分）；② 通电插座 `powerW = ratedW`、`energyKwh` 按分钟累加 |

> ⚠️ **停泵发生在"到点后的第一个整分"**，所以实际停泵时间最晚会比 `waterEndTime` 晚约 60 秒 —— 这是正常现象，不是没停止。
> ⚠️ **本机只能启动一个后端实例**：多开会让定时任务重复触发、水量双倍扣减、用电量翻倍。
> 控制台对应打印 `[环境监测]`、`[定时浇水]`、`[设备定时]`。

  "images": "[\"lamp.png\"]", "price": 199.00, "originPrice": 249.00,
  "stock": 100, "sales": 320, "detail": "……", "status": 1 }

// CartItem 结构（GET /api/cart/list）
{ "id": 1, "goodsId": 1, "goodsName": "米家智能台灯 Lite",
  "goodsCover": "lamp.png", "price": 199.00, "quantity": 2 }

{
  "addressId": 1,
  "items": [ { "goodsId": 1, "quantity": 2 } ]
}
// 响应 data：订单对象（含 items 明细）

{ "id": 1, "orderNo": "20260918120000123", "totalAmount": 398.00,
  "status": 1, "createTime": "2026-09-18 12:00:00",

## 十、状态速记（给前端）

| 场景 | 判断 |
|------|------|
| 未登录跳登录页 | `code === 401` → `HttpClient` 已统一清 token、Toast、跳登录（未登录提示"请先登录"，已登录提示"登录已过期"） |
| 业务失败 | `code !== 200` → `HttpClient` 已统一 Toast `msg`，页面不用重复提示 |
| 控制设备后刷新 | 直接用响应里的 `data`（最新设备对象）覆盖本地，以服务端为准 |
| 想拿"最新"数据 | 轮询概览接口即可；`overview` 已含房间+设备+环境三份数据，不要拆成三个请求 |
