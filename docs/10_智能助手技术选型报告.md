# 10 智能助手技术选型报告

> 项目：米家风格智慧家居 App（鸿蒙 ArkTS + Spring Boot + 华为云 IoTDA）
> 文档目的：对"App 内嵌智能助手"功能的技术路线进行比较与选型，说明选择依据。

## 一、选型目标与约束

| 目标 | 说明 |
|---|---|
| 演示可靠 | 答辩现场能稳定复现，不依赖运气 |
| 工作量小 | 小组课设周期内可完成（≤3 天） |
| 复用现有架构 | 不改动已打通的设备控制链路 |
| 成本可控 | 免费额度覆盖演示与日常使用 |
| 国内可用 | 模型服务可在国内直接注册与访问 |

现有技术基座：Spring Boot 3.3.4 + Hutool 5.8.27（HTTP/JSON）+ MyBatis-Plus；前端 ArkTS；设备控制已由 `DeviceService.control()` / `setMode()` 封装完成。

## 二、总体路线选型

### 候选方案

| 方案 | 思路 | 工作量 | 自然语言理解 | 主要风险 |
|---|---|---|---|---|
| A 规则匹配 | 关键词/同义词表解析指令 + FAQ 表直接命中 | 0.5 天 | 只认预设问法 | 问法稍变即失败 |
| B 大模型函数调用 | 后端调大模型 API，模型输出结构化工具调用，后端执行 | 1.5~2 天 | 换说法也能理解 | 依赖外部 API 与网络 |
| C 端侧/本地模型 | 在开发板或本地部署小模型（Ollama 等） | 5 天以上 | 一般 | 部署复杂、硬件受限、效果差 |

### 对比分析

- 方案 A 成本最低、100% 可控，但"太热了开个风扇"这类不在预设列表的话无法处理，演示时被动。
- 方案 B 用少量工作量换来自然语言理解与答辩亮点；风险（API 可用性）可通过"规则直答层 + 兜底话术"控制到演示级可靠。
- 方案 C 部署与调优成本远超收益，训练/微调更超出课程项目范围。

**结论：采用方案 B 为主路线，同时实现方案 A 的规则直答层作为高频指令的快速通道与降级兜底。**

## 三、大模型选型

### 候选比较

| 模型 | 费用 | 函数调用 | 国内注册 | 上下文长度 | 备注 |
|---|---|---|---|---|---|
| 智谱 GLM-4-Flash | 免费 | 支持 | 直接注册 | 128K | 免费且能力足够，首选 |
| DeepSeek V3 | 注册赠送，价格极低 | 支持 | 直接注册 | 64K~128K | 备选 |
| 通义千问 qwen-turbo | 有免费额度 | 支持 | 直接注册 | 128K | 备选 |
| OpenAI GPT 系列 | 付费，国内访问不便 | 支持 | 受限 | — | 不选 |
| 本地 Ollama 小模型 | 0 | 部分支持 | — | 小 | 效果与硬件不满足，不选 |

**结论：首选智谱 GLM-4-Flash（完全免费、支持 function calling、国内直连）；接口按 OpenAI 兼容格式封装，切换供应商只需改 base_url 与 key。**

## 四、关键设计选型

### 4.1 接入方式：HTTP 直调，不用官方 SDK

- 智谱 API 为标准 HTTPS + JSON，用项目已有的 Hutool `HttpUtil` 即可完成，无需引入新依赖。
- 收益：依赖零增加，与现有代码风格一致，组员易维护。

### 4.2 知识库方案：Prompt 注入，不做向量检索（RAG）

| 方案 | 适用数据量 | 工作量 | 结论 |
|---|---|---|---|
| Prompt 直接注入 | ≤ 数千字 | 0.5 天内 | 本项目 FAQ 规模小，选用 |
| RAG（向量库检索） | 海量文档 | +2~3 天（embedding、向量库、检索链路） | 数据量不需要，不选 |

知识分两类：
- 动态状态（设备列表/开关/环境值）：每次请求从数据库实时拼装，保证"模型说的"与"App 显示的"一致；
- 静态知识（联动规则、FAQ）：整理后写入 system prompt，后续可迁移到 `qa_knowledge` 表做热更新。

### 4.3 工具调用设计：白名单 + 参数校验

只暴露 3 个工具，全部映射到现有服务层：

| 工具 | 映射实现 | 说明 |
|---|---|---|
| `set_device_power` | `DeviceService.control()` | 复用已验证的控制链路（下发华为云命令） |
| `set_home_mode` | `DeviceService.setMode()` | 复用模式切换接口 |
| `query_device_status` | 直查 device/room_environment 表 | 只读 |

安全约束：
- 模型返回的工具调用在后端二次校验（房间名/设备名必须存在于数据库）；
- 不向模型暴露删除设备、修改房间等管理能力；
- 工具执行轮数上限 2 轮，防止异常循环。

### 4.4 对话管理：内存会话，不落库

演示场景按用户 ID 保留最近 10 轮（`ConcurrentHashMap`），进程重启即清空。理由：需求报告明确聊天记录不持久化，建表收益低。

### 4.5 App 端方案

| 项 | 选择 | 理由 |
|---|---|---|
| UI 形态 | 独立聊天页（消息列表 + 输入框），首页加入口 | 与主功能隔离，改动面小 |
| 通信方式 | 普通 HTTPS POST，非流式 | 避免 SSE 增加前端复杂度；"加载中→整段显示"演示可接受 |
| 网络层 | 复用现有 HttpClient | 无新依赖 |

## 五、风险与应对

| 风险 | 应对 |
|---|---|
| 答辩现场网络差、API 超时 | 规则直答层覆盖高频指令；失败返回兜底话术；备演示录屏视频 |
| 免费额度用尽 | GLM-4-Flash 免费不限量；备选 DeepSeek 切换成本低（改配置即可） |
| 模型输出不合规格的工具参数 | 参数校验失败即拒绝执行，回复"无法完成该操作" |
| 模型答非所问 | FAQ 与联动规则写入 system prompt；演示前按脚本全量自测 |

## 六、选型结论汇总

| 决策项 | 选型 |
|---|---|
| 总体路线 | 大模型 Function Calling 为主 + 规则直答为兜底 |
| 大模型 | 智谱 GLM-4-Flash（备选 DeepSeek），OpenAI 兼容接口 |
| 接入方式 | Hutool HttpUtil 直调 HTTPS，不引 SDK |
| 知识库 | Prompt 注入（动态状态实时拼装 + 静态 FAQ），不做 RAG |
| 工具范围 | set_device_power / set_home_mode / query_device_status 三项白名单 |
| 会话存储 | 内存保留 10 轮，不落库 |
| App 端 | 独立聊天页 + 首页入口，普通 POST 非流式 |
| 预计工作量 | 后端 1 天 + 前端 0.5~1 天 + 知识库整理与联调 0.5 天 |
