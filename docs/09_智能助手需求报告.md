# 09 智能助手需求报告

> 项目：米家风格智慧家居 App（鸿蒙 ArkTS + Spring Boot + 华为云 IoTDA）
> 文档目的：明确"App 内嵌智能助手"功能的需求范围、功能清单与验收标准，作为开发与答辩演示的依据。

## 一、背景与问题

本项目已完成智慧家居核心链路：设备端（STM32 + ESP8266）→ 华为云 IoTDA → AMQP 推送 → Spring Boot 后端 → 鸿蒙 App，支持设备控制、自动/手动模式、环境监测等功能。

当前 App 的操作方式以"点按"为主：用户需要进入对应房间、找到设备卡片再进行操作。对于"太热了，把风扇打开"这类自然表达，App 无法理解；对新用户来说，联动规则（天黑开灯、烟雾报警等）也需要一个入口去了解。

为此提出"智能助手"需求：在 App 内提供一个对话入口，能够回答智慧家居相关问题，并直接替用户完成简单操作。

## 二、目标用户与使用场景

目标用户为智慧家居 App 的普通家庭成员。典型场景：

| 编号 | 场景 | 用户原话示例 |
|---|---|---|
| S1 | 了解当前居家状态 | "现在家里温度怎么样？" |
| S2 | 自然语言控制设备 | "太热了，帮我把风扇打开" / "把客厅灯关了" |
| S3 | 切换全屋模式 | "帮我切换到自动模式" |
| S4 | 咨询联动规则与使用方法 | "烟雾报警是怎么工作的？"、"怎么添加设备？" |
| S5 | 查询设备状态 | "客厅的灯现在是开着吗？" |

## 三、功能需求

### FR1 智慧家居问答（优先级：高）

- 助手能回答项目 FAQ 与联动规则相关问题（烟雾报警逻辑、自动/手动模式区别、环境监测含义、设备配网流程等）。
- 知识来源：项目整理的 FAQ 知识库 + 设备实时状态。
- 验收：预设 FAQ 中的问题均能得到正确、通顺的回答。

### FR2 自然语言设备控制（优先级：高，演示核心）

- 用户以自然语言表达控制意图，助手识别后直接执行。
- 支持的操作限定为：设备开关（灯/风扇/自动门/蜂鸣器）、全屋模式切换。
- 指令中包含的房间、设备必须真实存在，否则助手应说明找不到该设备，不得执行。
- 验收："太热了，帮我把风扇打开"执行后，风扇实际开启（云端命令下发 + 数据库状态更新 + App 界面同步）。

### FR3 实时状态查询（优先级：中）

- 助手能根据数据库中的实时数据回答"某房间温度多少"、"某设备是否开启"等问题。
- 验收：回答与 App 界面显示的数据一致。

### FR4 多轮上下文（优先级：低）

- 同一会话内能理解指代，如"把灯打开……谢谢，再帮我关掉"。
- 会话历史保留最近 10 轮，仅存内存，不落库。

### FR5 异常兜底（优先级：高）

- 大模型服务不可用时，助手返回固定提示话术，并给出 FAQ 兜底回答，App 不白屏、不报错。
- 用户问出知识库与工具范围之外的问题时，礼貌说明能力边界。

### FR6 聊天界面（优先级：高）

- 新增聊天页面：消息列表（区分用户/助手气泡）、底部输入框、发送按钮。
- 首页提供助手入口。
- 等待回复期间有明确的加载状态，防止重复发送。

## 四、非功能需求

| 类别 | 要求 |
|---|---|
| 响应时间 | 常规问答 3 秒内返回；控制类指令从发送到设备动作 5 秒内 |
| 安全 | 助手只能调用白名单操作（设备开关、模式切换、状态查询），不可删除设备、修改房间；模型返回参数需校验 |
| 稳定性 | 模型调用失败有兜底话术；答辩演示场景下功能可重复演示 |
| 隐私 | 聊天记录只存内存（最多 10 轮），不持久化；不向模型发送用户密码等敏感信息 |
| 兼容 | 不影响现有设备控制、模式切换、环境监测等功能 |

## 五、边界（本期不做）

- 不做连续语音对话与语音识别（只做文字输入）。
- 不做打字机式流式输出（等整段返回后一次性显示）。
- 不做设备添加/删除、房间管理等管理类操作的语言控制。
- 不做个性化记忆（如记住用户习惯）。

## 六、验收演示脚本

1. "现在家里温度怎么样？" → 回答阳台温湿度光照实时值
2. "太热了，帮我把风扇打开" → 风扇实际转动，App 设备卡状态同步
3. "烟雾报警是怎么工作的？" → 正确回答联动规则
4. "帮我切换到手动模式" → 全屋模式卡变为手动
5. 断网/模型不可用时提问 → 显示兜底话术，不崩溃
