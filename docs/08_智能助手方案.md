# 08 App 智能助手方案（答辩演示用）

> 目标：在 App 里内嵌一个对话助手，能回答智慧家居相关问题，并帮用户执行简单操作（开灯、切模式等）。
> 定位：答辩演示功能，追求"能演示、稳定、工作量小"，不追求通用智能。

## 一、结论先行

**推荐方案 B：后端接入大模型 API（Function Calling），1.5~2 天工作量。**
如果时间紧张或不想注册任何 API，退回方案 A（纯规则匹配，0.5 天），答辩也够用。

| | 方案 A：规则匹配 | 方案 B：大模型 + 函数调用 | 方案 C：端侧模型 |
|---|---|---|---|
| 工作量 | 0.5 天 | 1.5~2 天 | 5 天以上 |
| 能听懂的话 | 只认预设问法 | 自然语言，换说法也能懂 | 自然语言 |
| 执行操作 | 直接代码解析 | 模型返回工具调用，后端执行 | 同 B |
| 答辩风险 | 问法之外的都答不上 | 依赖网络和 API 额度 | 部署复杂 |
| 费用 | 0 | 免费额度足够演示 | 0 |
| 亮点 | 低 | 高（答辩加分项） | 高但不可控 |

方案 C（在开发板上跑本地模型）部署难度大、效果差，不推荐。

## 二、推荐方案 B 的架构

```
App 聊天页(ArkTS)
   │  POST /api/assistant/chat { "question": "帮我关掉客厅的灯" }
   ▼
后端 AssistantService
   │  1. 组装上下文：当前设备列表+状态、全屋模式、联动规则说明、知识库问答
   │  2. 调大模型 API（带工具定义）
   ▼
大模型（如智谱 GLM-4-Flash / DeepSeek）
   │  返回两种结果之一：
   │  ① 普通回答文本（知识问答）
   │  ② 工具调用请求 set_device(room=客厅, device=灯, power=off)
   ▼
后端执行工具调用
   │  复用现有 DeviceService.control() / setMode()，执行后把结果回传给模型
   ▼
模型生成最终回复 → App 显示"已帮你关掉客厅灯"
```

关键点：**后端已有完整的控制链路**（DeviceService.control 会下发华为云命令并同步数据库），智能助手只是加了一个"用自然语言翻译成 DeviceService 调用"的入口，不碰任何硬件代码。

## 三、实现细节

### 3.1 模型选择（国内可直接注册，都有免费额度）

| 模型 | 免费情况 | 说明 |
|---|---|---|
| 智谱 GLM-4-Flash | 完全免费 | 支持 function calling，推荐首选 |
| DeepSeek chat | 注册送额度，价格极低 | 支持 function calling |
| 通义千问 qwen-turbo | 有免费额度 | 支持 function calling |

注册拿到 API Key 后，后端用 Hutool 的 HttpUtil 直接发 HTTP 请求即可，**不需要装任何 SDK**。

### 3.2 知识库（两种知识，分开处理）

1. **动态知识（每次请求都带）**：从数据库拼一段"当前家庭状态"文本——房间列表、每台设备的名字/类型/开关状态、全屋模式。模型靠它才知道"客厅灯现在开着"。
2. **静态知识（启动时加载或写进 prompt）**：
   - 联动规则说明（天黑开灯、升温开风扇、来人开门、烟雾报警）
   - 项目 FAQ（怎样切换自动模式、烟雾报警怎么触发、设备怎么配网）
   - 存一张 `qa_knowledge` 表（question / answer / keywords），也可以直接写在一个文本常量里。演示场景数据量小，直接塞 system prompt 最简单。

### 3.3 工具定义（给模型的能力清单）

只需暴露 3 个白名单工具，模型不能做任何白名单之外的事：

| 工具名 | 参数 | 对应现有代码 |
|---|---|---|
| `set_device_power` | roomName, deviceType/deviceName, power(on/off) | DeviceService.control |
| `set_home_mode` | mode(AUTO/MANUAL) | DeviceService.setMode |
| `query_device_status` | roomName(可选) | 直接查库返回文本 |

### 3.4 后端改动清单（全部新增，不动旧代码）

- `entity/QaKnowledge.java` + mapper（可选，FAQ 少可省）
- `service/AssistantService.java`：组 prompt、调模型、解析工具调用、循环执行（最多 2 轮）
- `controller/AssistantController.java`：`POST /api/assistant/chat`
- `application.yml` 加 `llm.api-key` 配置
- 聊天历史存内存（Map<userId, List>，保留最近 10 轮）即可，不用建表

### 3.5 App 端改动

- 新增聊天页 `pages/assistant/AssistantPage.ets`：消息列表 + 底部输入框 + 发送按钮（结构可参考已有的 fake-chat 练习项目）
- 首页右上角"+"旁加一个助手入口图标（或底部 Tab 加一位）
- 请求走 HttpClient，普通 POST 即可。不追求打字机流式效果（SSE 会明显增加工作量，演示时"转一下再出整段回答"完全可接受）

## 四、兜底与稳定性（答辩现场保命）

1. **高频问题走规则直答**：在 AssistantService 里先做一层关键词匹配（"打开客厅灯"这类标准指令直接调 control，不经过模型），响应快且 100% 成功；匹配不上再走模型。
2. **API 挂了不要白屏**：模型调用失败时返回固定话术"助手暂时不可用，您可以直接在房间页控制设备"，并附上预设 FAQ 的兜底回答。
3. **限制执行范围**：工具调用只允许 power/mode，不允许删除设备、改房间等危险操作；后端对模型返回的参数做校验（房间名/设备名必须真实存在）。
4. **演示前自测一遍**：把准备演示的问法全部跑一次，把答得不好的问答补进 FAQ。

## 五、答辩演示脚本（建议）

1. "现在家里温度怎么样？" → 模型读设备状态回答温湿度光照（知识问答）
2. "太热了，帮我把风扇打开" → 模型发工具调用 → 后端下发华为云命令 → 设备真的转起来（自然语言控制，全场最亮眼）
3. "烟雾报警是怎么工作的？" → FAQ 回答联动规则
4. "帮我切换到手动模式" → setMode 工具 → App 模式卡同步变化
5. 追问环节：说明架构（意图识别→工具调用→复用现有控制链路），强调"白名单工具+参数校验"保证安全

## 六、工作量估算

| 事项 | 时间 |
|---|---|
| 注册模型 API + 后端 AssistantService/Controller | 1 天 |
| App 聊天页 UI + 接口对接 | 0.5~1 天 |
| FAQ 整理 + 演示脚本自测 | 0.5 天 |

总计 **2~2.5 天**（方案 A 兜底版 0.5 天：只做关键词解析 + FAQ 表，无模型）。

## 七、决策建议

- 组员有余力、答辩想要亮点 → 直接做方案 B
- 只剩几天时间、保稳定 → 方案 A（关键词 + FAQ 表），把预设问法做全一样能演示
- 无论哪个方案，演示设备最好同时备一份"录屏视频"，防现场网络问题
