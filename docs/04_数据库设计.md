### 1.1 room_environment（环境监测表，2026-09 新增）

```sql
CREATE TABLE room_environment (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  room_id     BIGINT NOT NULL COMMENT '所属房间',
  temperature DECIMAL(4,1) DEFAULT 26.0 COMMENT '温度 ℃',
  humidity    INT DEFAULT 58 COMMENT '湿度 %',
  aqi         INT DEFAULT 45 COMMENT '空气质量指数',
  co2         INT DEFAULT 620 COMMENT '二氧化碳 ppm',
  smoke       INT DEFAULT 3 COMMENT '烟雾 ppm',
  gas         INT DEFAULT 0 COMMENT '燃气 ppm（非厨房恒为 0）',
  has_gas     TINYINT DEFAULT 0 COMMENT '1=该房间支持燃气检测（厨房）',
  smoke_alarm TINYINT DEFAULT 0 COMMENT '1=烟雾超阈值',
  gas_alarm   TINYINT DEFAULT 0 COMMENT '1=燃气超阈值',
  update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_room (room_id)     -- 一个房间只能有一条环境记录
);
```

**为什么单独建表？（这是本次设计的核心决策）**

| 旧做法 | 现做法 |
|--------|--------|
| 取房间内第一台 `temp_sensor` 设备，parse 它的 `status` JSON | `room_environment` 强类型字段，直接做阈值判定 |
| 用户删掉温湿度计 → 环境数据整个消失 | 环境与设备完全解耦 |
| 想加"CO₂/烟雾/燃气"就得往 JSON 里堆 key，类型全靠约定 | 每项一个字段，语义明确 |
| 得先造一台假"温湿度计"设备 | 新建房间时 `loadOrInit` 自动补一条 |

**`has_gas` 的语义**：房间名包含「厨房 / 厨 / 燃气 / 灶」时置 1（后端 `GAS_ROOM_KEYS` 维护）。
值为 0 时，接口返回的 `gas` 为 **`null`** 而不是 `0` ——
让前端能区分"这里没有燃气这项"和"有但浓度为 0"。

**报警位的维护**：`smoke_alarm` / `gas_alarm` 是**冗余字段**，由 `judgeAlarms()` 在
每次写入（定时采样 / 手动刷新）时按阈值重算。冗余的目的是让"查有哪些房间在报警"变成一条 SQL。
另外 CO₂（>1500）和 AQI（>150）不单独存位，由 `alarmCountOf()` 实时比较 ——
它们的阈值调整更频繁，不落库反而更省心。

## 二、设计要点

1. **设备状态用 JSON 字段**：不同类型设备属性不同（灯有亮度、空调有温度），
   统一存 `status` JSON 字符串，避免为每种设备建表。后端读取时 `JSONUtil.parseObj()` 转对象返回。
2. **数据隔离靠 user_id**：room/device/scene/cart/order 都挂 user_id，
   业务层校验归属（如 `checkRoomOwner`），防止越权操作他人数据。
3. **订单项冗余商品快照**：`goods_name`、`goods_cover`、下单时 `price`，
   商品之后改价/下架，历史订单显示仍正确。
4. **金额用 DECIMAL(10,2)**，Java 里对应 `BigDecimal`，绝不用 float/double。
5. **产品与商品分离**：`product` 只做介绍（参数、卖点、联动说明），
   `goods` 才能买，通过 `related_goods_id` 关联实现「产品详情 → 去商城看看」。
6. **模拟机制**：设备控制 = 后端合并 status JSON 写库；**环境数值 = 后端定时任务每 30 秒随机微调 `room_environment`**。
7. **环境与设备解耦**：环境监测数据（温湿度/空气质量/CO₂/烟雾/燃气）存在独立的 `room_environment` 表，
   **一个房间一条**，不挂在任何设备上。2026-09 起 `temp_sensor`（温湿度计）设备类型已彻底移除。

### 设备 `status` JSON 字段清单（按类型）

`status` 是 `VARCHAR(500)` 的 JSON 字符串，**不同设备类型字段不同**，
后端 `control()` 用 `Map.putAll()` 合并，所以新增字段**后端零改动**即可支持
（2026-09-23 起前面多了一道 `sanitizeAction()` 清洗，见本节末尾）。

| type | 字段 | 说明 |
|------|------|------|
| `light` | `power`, `brightness`, `colorTemp` | 开关 / 亮度 1-100 / 色温**仅** 2700 暖光、4000 自然、6500 冷白 |
| `ac` | `power`, `temperature`, `mode`, `fanSpeed`, `swing` | 开关 / 温度 16-30 / 模式 cool·heat·dry·fan·auto / 风速 0 自动·1 低·2 中·3 高 / 扫风 0 关·1 上下·2 左右·3 上下+左右 |
| `socket` | `power`, `ratedW`, `powerW`, `energyKwh` | 开关 / 额定功率 W / 实时功率 W（**只读**，通电=额定、断电=0）/ 累计用电 kWh（**只读**，按分钟累加） |
| `curtain` | `openPercent`, `power` | 开合 0-100（0 = 关；`power` 由后端联动写） |
| **`pump`** | `power`, `watering`, `duration`, `waterLevel`, `waterPlan`, `waterStartLevel`, `waterStartTime`, `waterEndTime` | 开关 / 是否抽水 0-1 / 本次浇水分钟数 1-60 / 水箱剩余 %（**只读**，浇水按 1%/分钟扣）/ 每日定时 `"HH:mm"`（空串=不定时）/ 开浇时水位 / 开浇时刻 / 预计停止时间 |
| **`lock`** | `power`, `locked`, `battery`, `keepOpen`, `lastUser`, `lastTime` | 开关（与 `locked` **反向**）/ 上锁 1、开锁 0 / 电量 %（**只读**）/ 常开模式 1（后端顺带置为开锁态）/ 最近开关门的人与时间（**只读**） |
| **全部 6 类** | `timerOn`, `timerOff` | 每日定时"开 / 关"，格式 `"HH:mm"`（空串=不定时），由 `DeviceTimedTask` 每分钟扫描执行 |

#### 定时开 / 关在各类型上的语义

| type | `timerOn` 到点 | `timerOff` 到点 |
|------|---------------|----------------|
| light / ac / socket | `power = on` | `power = off` |
| curtain | `openPercent = 100`（全开） | `openPercent = 0`（全关） |
| pump | `watering = 1`（按 `duration` 浇一次） | `watering = 0`（停浇并结清水量） |
| lock | `locked = 0`（开锁） | `locked = 1`（上锁） |

> **四条联动规则**（都写在 `DeviceServiceImpl.applyLinkage()` 里，前端只发语义字段，不发 `power`）：
> 1. 窗帘：`openPercent` → `power`（0=off，>0=on）；
> 2. 水泵：`watering` → `power`（1=on，0=off），并补 `duration` / `waterEndTime`；
> 3. 门禁：`locked` → `power`（**反向**：1=off，0=on）；
> 4. 门禁：`keepOpen=1`（常开模式）→ 顺带置 `locked=0`、`power=on`。
>
> 目的：设备卡片上的开关圆点、详情页的专属按钮、滑杆三者**永远不会互相矛盾**。
>
> ⚠️ 卡片 / 详情页的开关**必须发语义字段**（`openPercent` / `watering` / `locked`）。
> 对这三种设备直接发 `power` 会绕过联动，把 `power` 与语义字段拆成两个互相打架的事实
> （卡片圆点是绿的、详情页却显示关着）。

#### 字段校验（`sanitizeAction()`，2026-09-23 新增）

"前端能改什么、能改成多少"只在后端定义一次，前端即使写错也污染不了数据：

- **只读字段直接丢弃**：`powerW`、`energyKwh`、`waterLevel`、`waterStartLevel`、`waterStartTime`、
  `waterEndTime`、`battery`、`lastUser`、`lastTime` —— 这些由后端或"设备上报"产生，
  允许下发就等于允许"凭空造水 / 伪造电量"；
- **数值越界报错**（`code=400`）：temperature 16-30、brightness 1-100、openPercent 0-100、
  fanSpeed 0-3、swing 0-3、locked/keepOpen 0/1、duration 1-60；
- **枚举白名单**：mode（cool/heat/dry/fan/auto）、colorTemp（2700/4000/6500）；
- **时刻格式**：timerOn / timerOff / waterPlan 必须匹配 `HH:mm`；
- 清洗后没有可执行项时返回 `没有可执行的控制项`。

## 五、环境监测阈值口径（只在一处维护）

阈值定义在 `DeviceServiceImpl` 的常量里，**数据库不存阈值** —— 改阈值不用动数据。

| 指标 | 字段 | 报警阈值 | 常量名 | 等级文案 |
|------|------|---------|--------|---------|
| 烟雾 | `smoke` | > 50 ppm | `SMOKE_ALARM` | 正常 / ⚠ 烟雾报警 |
| 燃气 | `gas` | > 200 ppm | `GAS_ALARM` | 正常 / ⚠ 燃气泄漏（仅 `has_gas=1`） |
| 二氧化碳 | `co2` | > 1500 ppm | `CO2_ALARM` | 清新 / 正常 / 偏高·建议通风 / 闷浊·请立即通风 |
| 空气质量 | `aqi` | > 150 | `AQI_ALARM` | 优 / 良 / 轻度污染 / 中重度污染 |
| 温度 | `temperature` | <18 或 >28 ℃ | —（仅 UI 上色，不入 alarmCount） | 偏冷 / 舒适 / 偏热 |
| 湿度 | `humidity` | <30 或 >70 % | —（仅 UI 上色，不入 alarmCount） | 干燥 / 舒适 / 潮湿 |

> `alarmCount`（告警项数）= 烟雾 + 燃气 + CO₂ + AQI 四项命中数；温湿度只影响**颜色**（橙/绿），不计入告警数。

## 六、数据库脚本（唯一一份）

整个项目**只有一份需要执行的 SQL 脚本**：`Mysql/init_all.sql` —— 自包含，可单独交付。

它做三件事：建库（`smart_home`，utf8mb4）→ 建 16 张表 → 写入全套演示数据
（1 用户 / 4 房间 / 19 设备 / 4 条环境 / 9 场景 / 8 产品 / 20 商品 / 7 轮播）。

脚本开头是 `DROP DATABASE IF EXISTS` + `CREATE DATABASE`，所以：

- **不用手动新建库、也不用先 `USE`**，直接执行整个文件即可（看到 `Unknown database 'smart_home'` 说明脚本没跑进去）；
- **可以反复执行**，每次都回到同一套干净的演示数据（演示前重置的标准动作）；
- 没有任何"分段互斥"结构，**不存在"执行整个文件会出错"的坑**。

> **演进说明**：这份脚本由早期的"一份建库脚本 + 多个老库增量升级脚本"合并而来 —— 曾用 5 个增量脚本
> 分别补 `operation_log` 表、`banner` 表与商品扩充、`room_environment` 表、阳台设备、
> `user` 的邮箱/手机号字段。增量内容已全部并入本脚本，原文件不再保留；
> 现在数据库结构完全由这一份文件定义，不需要再维护任何"升级补丁"。

> ⚠️ **导入必须指定 utf8mb4**：命令行要 `mysql --default-character-set=utf8mb4 < init_all.sql`，
> Navicat 要在连接属性里选 utf8mb4。否则中文（房间名/设备名/商品名/轮播标题）会在入库时变成 `?`，
> **且不可逆**（信息已丢失，只能重新导入）。项目里真实踩过这个坑。

### 6.1 改数据库结构时的三条硬规则

1. **新建设备必须追加在 `device` 表末尾** —— `scene_action.device_id` 是按自增 id 硬引用的，
   中间插入会把后面所有设备的 id 顶掉（本项目就有过 `id=3` 厨房插座被删、场景引用改指向 `id=4` 的情况）。
   演示数据里阳台的两台设备就排在最后（`id=7`/`id=8`），场景不引用它们。
2. **`JSON_SET` 不能把 `JSON_EXTRACT(...) IS NULL` 当第三个参数传**，会报
   `ERROR 1582 Incorrect parameter count`；必须写
   `JSON_SET(status, '$.k', COALESCE(JSON_EXTRACT(status,'$.k'), 默认值))`，字符串字段还要套 `JSON_UNQUOTE`。
3. **改结构要同步三处**：本文档、`Mysql/init_all.sql`；若影响接口出入参，还要同步 `03_接口文档.md`。
