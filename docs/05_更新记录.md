## 二、功能修正

### 2.1 水泵水箱水量：不能手调，改为「浇水按分钟消耗」

#### 问题现象

设备详情页的水泵面板上有一个**水箱水量滑杆**，拖着就能把水量设成任意值；
而且**浇水中水量纹丝不动**，只有停泵那一刻才一次性跳掉一大截，看起来像"浇了水却没消耗"。

#### 根因（两处，都在后端）

1. **状态可以被前端直接覆盖**：`DeviceServiceImpl.control()` 里是

   ```java
   Map<String, Object> status = JSONUtil.parseObj(device.getStatus());
   status.putAll(action);            // ← 前端发什么就写什么
   ```

   前端滑杆发的 `{"waterLevel": 60}` 被原样塞进设备状态，水量可以被凭空设定。

2. **扣水时机错**：旧 `tickWatering()` 只在**到点停泵那一刻**做一次 `waterLevel -= duration`，
   浇水的十分钟里水位没有任何变化——而且**只在停泵时写库**，中途根本查不到变化。

#### 修复方案

**核心思路**：水量**只能由"浇水时长"推导**，不能由外部设定；且推导必须是**幂等**的（定时任务重复跑不会多扣）。

**① 开泵时记下起点**（`startWatering`）：

```java
private void startWatering(Map<String, Object> status, int dur) {
    int level = status.get("waterLevel") instanceof Number
            ? ((Number) status.get("waterLevel")).intValue() : 80;
    status.put("watering", 1);
    status.put("power", "on");
    status.put("duration", dur);
    status.put("waterStartLevel", level);                       // ← 开浇时的水位
    status.put("waterStartTime", LocalDateTime.now().format(TIME_FMT));  // ← 开浇时刻
    status.put("waterEndTime", LocalDateTime.now().plusMinutes(dur).format(TIME_FMT));
}
```

**② 新增 `syncWaterLevel()`：由起点推算，而不是"每跑一次扣一格"**

```java
/** 剩余水量 = 开浇水位 − 已浇分钟数（1%/分钟，封顶 duration，封底 0）
 *  由起点推算 → 幂等：定时任务跑 1 次还是 10 次，结果一样 */
private void syncWaterLevel(Map<String, Object> status) {
    ...
    long elapsed = Duration.between(start, now).toMinutes();
    elapsed = Math.min(elapsed, duration);
    status.put("waterLevel", Math.max(0, startLevel - (int) elapsed));
}
```

**③ `tickWatering()` 改成每分钟都同步 + 落库**（这是"浇水中能看到水位下降"的关键）：

```java
syncWaterLevel(status);          // 每分钟把水位往前推一格
if (!now.isBefore(end)) {        // 到点 → 停泵
    status.put("watering", 0);
    status.put("power", "off");
    status.put("waterStartTime", "");   // 清起点，之后不再推算
}
deviceMapper.updateById(dev);    // 每分钟写库，前端轮询才能看到
```

**④ 手动停泵也先结清**：`applyLinkage()` 里收到 `watering=0` 时先调 `syncWaterLevel()`，
把已经浇掉的分钟数算进去，再清起点。

**⑤ 接口层面堵死**：`control()` 对水泵**直接丢弃指令里的 `waterLevel`**：

```java
// 水箱水量只允许"浇水消耗"产生：指令里带 waterLevel 一律丢弃
if ("pump".equals(device.getType()) && action.containsKey("waterLevel")) {
    log.warn("[设备控制] 忽略水泵 waterLevel 指令（水量只能由浇水量决定）");
    filtered.remove("waterLevel");
}
```

**⑥ 前端**：详情页的水箱 `Slider`（滑杆）换成**只读 `Progress` 进度条**；
浇水中显示提示文案「浇水中，水量按分钟消耗」；`DeviceAction` 里的 `waterLevel` 字段删除。

#### 验证结果

`.scan/pump_verify.py` 打真接口自测，**9/9 全过**：

| 验证点 | 结果 |
|--------|------|
| 手动发 `{"waterLevel":100}` | 被丢弃，水量仍为 78 ✅ |
| 开泵后记录起点（`waterStartLevel`/`waterStartTime`） | 写入正确 ✅ |
| 开浇瞬间不立刻扣水 | 水位不变 ✅ |
| 到点自动停泵 | `watering` 归 0、`power` 变 off ✅ |
| 停泵后水量按分钟扣减 | 78 → 77 ✅ |
| 中途手动停泵 | 已浇分钟数正确结清（80 → 78） ✅ |

#### 两个坑（下次别再踩）

- **定时任务节拍是整分第 0 秒**（`cron = "0 * * * * ?"`）。所以"到点停泵"实际发生在
  `waterEndTime` 之后的**第一个整分**，最晚比 `waterEndTime` 晚约 60 秒。
  测试等待窗口必须**大于一个完整节拍**（第一轮只等 70 秒就误判成"停泵没生效"）。
- `POST /api/device/{id}/water` 的 `duration` 是**从 body 读**的（不是 query 参数）。

### 2.2 广告页「跳过」按钮归位右上角

**问题**：按钮出现在屏幕右侧偏中间，不在右上角。

**原因**：`Stack` 默认 `alignContent: Center`，里面的 `Row` 高度只有内容那么高，
于是被**垂直居中**到屏幕中部。

**修复**：给 `Stack` 指定对齐方式，让内容贴顶：

```typescript
Stack({ alignContent: Alignment.TopEnd }) {
  Image($r('app.media.img_ad')).width('100%').height('100%').objectFit(ImageFit.Cover)
  Row() { Text(`跳过 ${this.seconds}`) /* … */ }
    .width('100%').justifyContent(FlexAlign.End).padding({ top: 48, right: 16 })
}
```

### 2.3 前端编译失败：色温胶囊行的选项数组类型不匹配

**问题**：3.4 的设备面板写完后，`hvigor ... assembleHap` 在 `CompileArkTS` 阶段直接失败：

```
1 ERROR: 10505001 ArkTS Compiler Error
Error Message: Argument of type 'NumberOption[]' is not assignable to parameter of type 'DeviceOption[]'.
  Type 'NumberOption' is not assignable to type 'DeviceOption'.
    Types of property 'value' are incompatible.
      Type 'number' is not assignable to type 'string'.
  At File: .../ets/pages/device/DeviceDetailPage.ets:556:30
COMPILE RESULT:FAIL {ERROR:2 WARN:166}
```

**原因**：`common/DeviceOptions.ets` 里按"取值是数字还是字符串"把选项数组分成了两类：

| 数组 | 声明类型 | `value` 类型 |
|------|----------|--------------|
| `AC_MODES` / `TIMER_TIMES` | `DeviceOption[]` | `string` |
| `AC_FAN_SPEEDS` / `AC_SWINGS` | `NumberOption[]` | `number` |
| `LIGHT_COLOR_TEMPS` | `NumberOption[]` | `number` |

详情页对应有两个胶囊行构造器：`chipRow(options: DeviceOption[], …)` 和
`numChipRow(options: NumberOption[], …)`。色温这一行写成了 `chipRow(LIGHT_COLOR_TEMPS, 'colorTemp')`
—— **数组是 `NumberOption[]`，构造器要 `DeviceOption[]`**，ArkTS 是强类型的，不做隐式兼容，直接编译不过。

**为什么之前没发现**：色温的读写逻辑（`currentStr` 的 `colorTemp` 分支、`pickStr` 里
`parseInt(value)`）本来就是按**字符串 value** 写的 —— 也就是说，代码的其余部分早就默认
"色温走字符串路径"，只有 `LIGHT_COLOR_TEMPS` 这一个声明还写着 `NumberOption[]`，属于自相矛盾。

**修复**：把 `LIGHT_COLOR_TEMPS` 改成 `DeviceOption[]`（`value` 用 `'2700' / '4000' / '6500'`），
与已有的字符串路径对齐；`colorTempName(v: number)` 里比较前加 `parseInt`：

```typescript
export const LIGHT_COLOR_TEMPS: DeviceOption[] = [
  { value: '2700', label: '暖光' },
  { value: '4000', label: '自然光' },
  { value: '6500', label: '冷白光' }
]

export function colorTempName(v: number): string {
  for (let i = 0; i < LIGHT_COLOR_TEMPS.length; i++) {
    if (parseInt(LIGHT_COLOR_TEMPS[i].value) === v) {
      return LIGHT_COLOR_TEMPS[i].label
    }
  }
  return '自然光'
}
```

> ⚠️ 注意区分「前端内部表示」和「下发给后端的 JSON」：前端选项表里色温是字符串，
> 点选时 `pickStr` 会 `parseInt` 成数字再塞进 `DeviceAction.colorTemp`，
> 后端 `sanitizeAction` 的白名单 `COLOR_TEMPS = {2700, 4000, 6500}` 校验的仍是**数字**，不受影响。

**教训**：同一族选项数组，要么统一成一个类型配一个构造器，要么两个构造器严格分派 ——
**别让"声明类型"和"使用路径"各说各话**。这个 bug 的位置（`LIGHT_COLOR_TEMPS` 的声明行）
和报错位置（`DeviceDetailPage.ets:556` 的调用行）不在一处，只看报错容易改错地方。

## 三、新增功能

### 3.1 广告启动页

**需求**：打开 App 就是广告；右上角「跳过」；15 秒后自动进首页；跳转后销毁、无法返回。

**实现文件**

| 文件 | 作用 |
|------|------|
| `pages/AdPage.ets` | 广告页本体（倒计时 / 跳过 / 拦截返回键） |
| `common/AppFlag.ets` | 跨页面存活的「广告是否已展示」标志 |
| `pages/Index.ets` | 冷启动时判断并跳转广告页 |
| `resources/base/media/img_ad.png` | 广告图（AI 生成） |

**关键点 1：跳转必须用 `replaceUrl`，不能用 `pushUrl`**

```typescript
enterApp() {
  this.stopCountdown()
  router.replaceUrl({ url: 'pages/Index' })   // 顶替掉广告页，页面栈里不留残影
}

onBackPress(): boolean { return true }        // 广告期间禁止返回
```

用 `pushUrl` 的话，广告页会一直压在页面栈里，用户在首页按返回键就又回到广告。

**关键点 2：启动页仍然是 `pages/Index`，不是广告页**

这里有个容易搞错的点：**`main_pages.json` 里页面的排列顺序并不决定首屏**，
首屏由 `EntryAbility` 的 `windowStage.loadContent(...)` 决定。

所以本项目的做法是：

```typescript
// EntryAbility.ets —— 首屏保持 Index 不变
windowStage.loadContent('pages/Index', (err) => { ... })
```

```typescript
// Index.ets —— 冷启动第一件事就是跳广告，用 replaceUrl 让 AdPage 顶替 Index
aboutToAppear() {
  if (!AppFlag.adShown) {
    AppFlag.adShown = true
    router.replaceUrl({ url: 'pages/AdPage' })
    return
  }
  ...
}
```

**关键点 3：为什么标志要放在独立文件里当 `static` 字段**

广告页结束是 `replaceUrl` 回 `Index`，**旧的 Index 实例会被销毁**。
如果标志是 Index 的成员变量，它会跟着实例一起重置 —— 新的 Index 又跳一次广告，
形成 `Index → 广告 → Index → 广告 …` 的**死循环**。

`static` 字段属于类本身、进程内只有一份，与页面实例的生死无关，因此能保证
**一次冷启动只弹一次广告**（杀掉 App 重开才会再弹）。这也正是 `common/AppFlag.ets` 单独存在的理由。

**实测**：模拟器截图确认——启动即广告页（右上角「跳过 13」倒计时）、15 秒自动进首页、
点「跳过」立即进首页、返回键无法退回广告页。

### 3.2 首页天气面板

**需求**：首页显示今日天气，数据来自和风天气 API，可切换城市，每 60 分钟刷新一次。

**实现文件**

| 端 | 文件 | 作用 |
|----|------|------|
| 后端 | `controller/WeatherController.java` | `GET /api/weather/now`、`GET /api/weather/cities` |
| 后端 | `service/impl/WeatherServiceImpl.java` | 调用和风 API + **10 分钟内存缓存** + 内置 33 城清单 |
| 后端 | `vo/WeatherNowVO.java` | 出参，字段与和风返回**一一对应** |

| 前端 | `model/Weather.ets` | `WeatherNow` / `WeatherCity` 模型 |
| 前端 | `view/WeatherPanel.ets` | 面板组件（放在 `HomePage` 顶部） |
| 配置 | `application.yml` → `qweather.api.*` | `url` / `key` / `location`（默认南昌 `101240101`） |

**为什么后端要代理、不直连**

1. 和风 KEY 不能写进前端（前端包可被反编译）；
2. 免费版有 QPS 限制，**后端加 10 分钟内存缓存**兜住，避免多个端同时刷爆配额；
3. 前端少一次跨域/证书往返。

**前端三个细节**

- **切走 Tab 要停表**：`@Prop @Watch('onVisibleChange') visible` 由 `HomePage` 传入，
  不可见就 `stopTimer()` —— Tabs 子页面切走**不会销毁**，不停表就是白刷接口；
- **未登录不发请求**：`sync()` 里先判 `TokenStore.isLogin()`；
- **ForEach 的 key 带 `value`**：数据一变 key 就变，组件才会用新数据重建（手册踩坑 14）。

面板内容：城市名（点击弹城市清单）+ 更新时间 + 天气图标 + 大温度 + 天气现象/体感 +
8 项指标格（湿度/风向/风速/降水量/气压/能见度/云量/露点）+ 观测时间。

| SQL | `docs/sql/_history_backup/upgrade_v5_email_phone_20260923.sql` | `user` 表加 `email`/`phone` 唯一索引（**已合入 `init_all.sql` 第二部分**，不必单独执行） |

**为什么用 Redis 而不是内存 Map**

验证码是典型的「短生命周期 + 高频读写」数据：`EXPIRE` 一行搞定 60 秒过期，
不用自己起清理定时器；多实例部署时验证码也是全局共享的（内存 Map 只能单机用）。

**防刷两条（`EmailCodeServiceImpl`）**

```java
// ① 60 秒冷却：key 还在 = 上一个码仍有效 → 拒绝重发
if (Boolean.TRUE.equals(redisTemplate.hasKey(key))) {
    throw new BizException("验证码已发送，60 秒内请勿重复获取");
}
// ② 一次性使用：校验通过立刻删 key，同一个码不能注册两次
redisTemplate.delete(key);
```

**发信失败必须回滚 key**（否则用户收不到信、又卡在 60 秒冷却里）：

```java
catch (Exception e) {
    redisTemplate.delete(key);
    throw new BizException("验证码邮件发送失败，请稍后重试");
}
```

**注册时 `username` 复用邮箱** —— 这样**老的 `username + password` 登录接口零改动**就能登录
（详见 `UserServiceImpl.registerByEmail`）。并发注册同一邮箱时，由数据库唯一索引兜底。

**本机前置条件**：Redis 需在跑（`D:\Soft\Redis`，6379）。没起 Redis 时发码接口会直接报连接失败。

#### 关键设计 1：定时做成"通用能力"，而不是每种设备写一套

所有设备的定时其实只有"开 / 关"两个终点，差别只是落到哪个语义字段上，
所以收敛成一个 `DeviceTimedTask` + 一个 `applyTimer()` 映射：

```java
// DeviceServiceImpl.applyTimer() —— "开 / 关" → 各类型自己的语义字段
if ("curtain".equals(type)) {
    status.put("openPercent", turnOn ? 100 : 0);      // 开 = 全开
} else if ("pump".equals(type)) {
    ... // 开 = 按 duration 浇一次；关 = 停浇并结清水量
} else if ("lock".equals(type)) {
    status.put("locked", turnOn ? 0 : 1);             // 开 = 开锁（反向）
} else {
    status.put("power", turnOn ? "on" : "off");       // 灯 / 空调 / 插座
}
```

以后新增设备类型，只要在这里补一行映射，6 类之外的新设备立刻就有定时能力。

**前端文案也跟着变**：同一个"定时开"，在空调上叫「开机」、在窗帘上叫「全开」、
在门禁上叫「开锁」、在水泵上叫「浇水」—— 由 `timerOnWord()` 按类型返回，
用户看到的是自己的设备语言，而不是抽象的"开 / 关"。

#### 关键设计 2：字段清洗 —— 前端能改什么，后端说了算

原来的 `control()` 是 `status.putAll(action)`，**前端发什么就写什么**。
这在演示里很危险：直接调接口就能把水箱加满、把用电量改成 999。

现在统一走 `sanitizeAction()`：

```java
// ① 只读字段一律丢弃（由后端/设备上报维护）
private static final Set<String> READONLY_KEYS = Set.of(
        "powerW", "energyKwh",      // 插座计量
        "waterLevel", "waterStartLevel", "waterStartTime", "waterEndTime",   // 水泵水量
        "battery", "lastUser", "lastTime");   // 门禁上报

// ② 数值越界直接报错（不悄悄夹取，问题尽早暴露）
clean.put(key, intRange(key, val, 16, 30));      // 温度

// ③ 枚举走白名单
if (!AC_MODES.contains(m)) throw new BizException("不支持的空调模式：" + m);
```

好处是**规则只在后端一处**：前端滑杆就算把温度发成 999，也污染不了数据。

#### 关键设计 3：顺手修掉一个既有缺陷（卡片开关发错字段）

`DeviceCard` 的开关圆点原来对所有设备都发 `{power: next}`。对灯/空调/插座没问题，
但**窗帘 / 水泵 / 门禁的 `power` 是由语义字段联动推导的** —— 直接发 `power` 会绕过联动，
把 `power` 和语义字段变成两个互相打架的事实：

> 点一下窗帘卡片的圆点 → 圆点变绿（`power=on`），
> 但 `openPercent` 还是 0 → 详情页显示"已全关"，两边对不上。

修复：`togglePower()` 按类型发**语义字段**（`openPercent` / `watering` / `locked`），
`isOn()` 也按各自的语义口径判断。这正是"语义字段驱动 power"这条约定本该覆盖到的地方。

## 四、环境与联调修复

### 4.1 前端后端地址配置（最常改的一处）

**唯一入口**：`smarthome_app/entry/src/main/ets/common/Env.ets`（页面里**禁止**写死地址）

```typescript
export class Env {
  // 第 4 行：真机联调 —— 改成后端电脑的局域网 IP（ipconfig 查看），手机与电脑同一 WiFi
  static readonly BASE_URL_DEV: string = 'http://172.16.101.70:8080'
  // 第 6 行：模拟器 —— 10.0.2.2 固定指向宿主机
  static readonly BASE_URL_EMULATOR: string = 'http://10.0.2.2:8080'

  // 第 9 行：当前用哪个环境 —— 切环境只改这一行
  static readonly BASE_URL: string = Env.BASE_URL_EMULATOR
}
```

**排查顺序**：App 连不上后端时，先确认这三点——

1. `BASE_URL` 指向的环境和你在用的设备**是否匹配**（模拟器 vs 真机）；
2. `BASE_URL_DEV` 里的 IP **是不是本机当前的局域网 IP**（换网络/重启路由器会变）；
3. 真机联调时电脑**防火墙是否放行 8080**（加规则需要管理员权限）。

> 本次踩坑：`Env.ets` 里原本是手册示例 IP `192.168.1.100`，本机实际是 `172.16.101.70`；
> 且 `BASE_URL` 指向 DEV 模式但实际跑的是模拟器 —— 两处都改完才通。

### 4.2 8080 端口被占用（Windows 特有）

**现象**：后端报 `Port 8080 was already in use`，但 `netstat` 查不到占用进程。

**原因**：Windows 的 **Hyper-V / winnat 会动态保留一段端口区间**，本机保留区间是 `8079–8178`，
正好把 8080 圈进去了。这类保留**不出现在进程列表里**，所以 `netstat` 查不到。

**两种处置**（都需要**管理员** PowerShell）：

```powershell
# 方案 A（推荐，可逆）：临时让出保留区，重启后端，再恢复
net stop winnat
# ... 启动后端 ...
net start winnat
```

```powershell
# 方案 B：把 8080 永久登记为"排除端口"，系统不再自动保留它
netsh int ipv4 add excludedportrange protocol=tcp startport=8080 numberofports=1 store=persistent
# 撤销（删除该排除项）：
netsh int ipv4 delete excludedportrange protocol=tcp startport=8080 numberofports=1
```

> 两个方案都**完全可逆**，不改代码、不改端口号、不动系统关键配置。
> 另一种情况是**僵死的 java 进程**（不监听端口也不响应）：用 `Stop-Process -Id <PID> -Force` 清掉即可。

### 4.3 中文全变 `?`（编码问题，只能重导）

**现象**：App 里房间名、设备名、商品名全是 `??`，但接口能正常返回。

**诊断**：直接查库看十六进制 ——

```sql
SELECT id, name, HEX(name) FROM smart_home.room;
-- 结果 HEX = 3F3F → 3F 就是英文问号 '?'，说明中文在**入库那一刻**就已经丢了
```

**结论**：不是 App 字体问题，是**导库时连接没有使用 utf8mb4**。
`3F` 是问号字符本身，信息已经**不可逆丢失**，`UPDATE` 也救不回来，**只能重新导入**。

**以后导库必须带字符集参数**：

```cmd
cmd /c "mysql -u root -p --default-character-set=utf8mb4 < docs\sql\init_all.sql"
```

Navicat / 图形客户端则在连接配置里把编码设为 `utf8mb4`。
`init_all.sql` 头部也补了这条命令的提示。

### 4.4 天气卡永远显示「获取中」

**原因**：`WeatherPanel` 首次加载失败时**静默吞掉**了结果 —— 没有错误提示、也没有重试，
只能等 60 分钟后的定时器，表现出来就是永远卡在「获取中」。

**修复**（`view/WeatherPanel.ets`）：

- 新增 `loadFailed` 状态 → 文案变成「**获取失败，点击重试**」，点击即重新拉取；
- 新增 **30 秒兜底自动重试**（`scheduleRetry()` / `stopRetryTimer()`），拿到数据自动停表；
- 成功/失败都不弹窗：天气是辅助信息，按节流原则静默处理即可。

## 八、注意事项

1. **后端只允许跑一个实例**：`SensorSimTask`（30 秒）/ `SceneTimedTask` / `WaterTimedTask`（每分钟）
   都在改数据，多开会导致数据翻倍。改完 Java 代码必须**重启进程**（不是只 Build）。
2. **默认端口 8080**：本机 6893 被其他程序占用，所以统一用 8080。IDEA 里 Run 前先确认没有别的实例在跑。
3. **数据库重置后登录态会失效**：App 需重新用 `demo / 123456` 登录（本地 token 指向的 user 已重建）。
4. **Redis 必须在线**：邮箱验证码功能依赖 Redis（`D:\Soft\Redis`，6379）。没起 Redis 时注册会失败。
5. **敏感信息**：`application.yml` 里的和风 KEY、QQ 邮箱授权码属演示用临时凭据，
   **不要外传或提交到公开仓库**；演示结束建议重置。
6. **定时任务节拍是整分第 0 秒**：涉及"到点触发"的测试，等待窗口要 > 1 分钟。
   现有 4 个定时任务：`SensorSimTask`（30 秒模拟环境）、`SceneTimedTask`、`WaterTimedTask`、`DeviceTimedTask`（后三个都是 `0 * * * * ?`）。
7. **设备卡片的开关圆点必须发语义字段**：灯/空调/插座发 `power`，窗帘发 `openPercent`、
   水泵发 `watering`、门禁发 `locked`。对后三种直接发 `power` 会绕过后端联动，造成状态自相矛盾。
8. **改前端控制面板时注意 ArkTS 的 `@Builder` 快照坑**：`@Builder` 的参数是**值快照**，
   状态变化不会刷新。所以详情页的选项行只在参数里传"选项数组 + 类别名"，
   选中判断与点击下发都通过 `this.xxx()` 现算 —— 参见 `DeviceDetailPage.ets` 的 `chipRow()`。
9. **选项数组的声明类型必须和使用它的构造器一致**：`DeviceOptions.ets` 里有两类选项
   （`DeviceOption` 字符串值 / `NumberOption` 数值值），详情页对应 `chipRow()` 和 `numChipRow()`。
   ArkTS 强类型不做隐式兼容，**传错数组会直接编译失败**（见 §2.3）。
   加新选项时先想清楚"这个字段下发的是字符串还是数字"，再决定用哪个数组。
10. **前端编译报错行号 = 调用处，根因常在别的文件**：`ArkTS` 报 `not assignable to parameter of type`
    时，先去看**实参的来源声明**，而不是改报错那行。这次的根因在 `common/DeviceOptions.ets`，
    报错却打在 `DeviceDetailPage.ets:556`。
11. **全量重编命令**（Windows PowerShell，先删 `entry\build` 再编）：

    ```powershell
    Set-Location "D:\Code\smarthome_project\smarthome_app"
    Remove-Item "entry\build" -Recurse -Force -ErrorAction SilentlyContinue
    $env:DEVECO_SDK_HOME = 'C:\Users\LENOVO\ohossdk'
    & "D:\Soft\Huawei\DevEco Studio\tools\node\node.exe" `
      "D:\Soft\Huawei\DevEco Studio\tools\hvigor\bin\hvigorw.js" `
      --mode module -p module=entry@default -p product=default assembleHap --no-daemon
    ```

    > 构建日志末尾若出现 `PROGRAM BLOCKED BY SECURITY POLICY - wmic.exe`，**属正常**：
    > hvigor 会在收尾阶段探测 `wmic` 而被安全策略拦掉。只要日志里已经打印了
    > `BUILD SUCCESSFUL` 且 HAP 产物已生成，这次构建就是成功的，**不要重试**。

## 十、文档整理：接口文档升级为「契约 + 命名规范」（2026-09-30）

### 10.1 为什么要改

原来的接口文档只有"端点清单 + 请求响应示例"，**缺三样东西**，导致同一件事在项目里出现多种写法：

1. **没有"方法名对照"** —— 组员总在问"我要改的接口前后端各叫什么"，得自己去翻代码；
2. **没有命名规范** —— 新接口的路径、方法名、字段名各凭感觉起，容易出现 `GET /api/device/getList` 这类不一致；
